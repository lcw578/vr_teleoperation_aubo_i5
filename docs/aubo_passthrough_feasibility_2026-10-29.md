# 当前遥操链路能否改用透传：可行性研究

日期：2026-10-29，时间按北京时间。范围为当前 AUBO i5、ServiceInterface 2.5.0、已有 Quest/IK 后端、既有实机日志与本地厂家资料。本轮只做源码、SDK 静态分析、历史数据重算及本机网口只读核对，没有连接 SDK、切换模式、运行机器人或修改控制代码与保护阈值。

## 判断

**现有 Quest → world 映射 → 六轴 IK 可以继续作为透传的上层目标来源，但目前的“最新 IK 位置直接透传、期望 200 Hz”实现不宜作为正式基线。** 要达到高频且平顺的控制，需要解决通信长尾，并增加适合透传的轨迹生成、首点衔接与送点管理；不是只换一个 SDK 函数。

透传值得作为独立后端继续研究，尚未证明在当前设备/链路上比 Follow 更快、更平顺。此前实际试验已经确认能进入、发送、退出；这些局部成功不等于持续供点、断流和停止语义已完整验收。ARCS `servoJoint` 是另一套 API，目前已知服务端口拒绝连接，不能与旧 TCP→CAN 透传混用结论。

术语上，纯 MuJoCo `kinematic` 仿真是约 200 Hz 的运动学预览，不调用 Follow。这里讨论的是复用仿真控制核心的**真机执行后端**；22 Hz 是实发运动请求频率，不是仿真 IK 的额定频率。

## 1. 22 Hz 与超时之间的真实关系

2026-10-29 12:35 的复测请求 25 Hz，实发约 22.244 Hz；3510 次 Follow 均返回成功。调用中位数 40.951 ms、P95 57.946 ms、最大 277.637 ms。25 Hz 的周期只有 40 ms，同步调用超过周期会推迟下一次发送，因此实际发送偏低符合代码和实测。它不是厂家 Follow 的已证实最高频率。

但 **22 Hz 本身不等于必然触发 200 ms 超时**：22 Hz 对应平均约 45 ms；异常停止更取决于 200 ms 级的长尾和哪个数据源失效。

- 12:35 的并行查询复测有 4 次运行状态过期、3 次 Quest 输入空档。4 次状态事件附近均存在 B 连接 TCP SACK 和字节缺口；不能靠切换 A 的运动函数修复 B 的状态过期或 Quest 输入空档。
- 16:18 的后续单连接 Follow 会话已将输入阈值设置为 1 秒，仍有 6 次关节反馈过期，最新回调年龄约 200–204 ms，对应 Follow 调用约 225–233 ms；这些调用未超过 500 ms SDK 预算。不能将输入超时、关节反馈过期与 SDK 调用超时混称为同一个问题。
- 10:45:47 的同步抓包确认 A 连接缺失 82 字节，后续应答与关节推送被 TCP 按序交付阻塞，补齐后回调和 Follow 一起恢复。这是已证实的一次底层阻塞，不能从时间相关性扩展为所有历史事件都已定位。

本轮重新读取 `/sys/class/net/enp3s0/{speed,duplex,operstate}`，结果仍是 `100 / half / up`。半双工需要优先核对；它本身尚不能证明双工不匹配或确定丢失位置。应确认柜端配置，再匹配两端协商/固定模式，不能猜测后单边强制全双工。低流量下，100 Mbps 带宽数值本身不是瓶颈证据。

## 2. 已有透传为什么没有跑到 200 Hz

本轮从原始 JSONL 重算，只取同一次接合内的 SDK 调用起点间隔，避免把松开等待纳入频率：

| 指标 | 2026-10-28 15:26 的透传试验 |
| --- | ---: |
| 请求频率 | 200 Hz，即 5 ms |
| 成功发送 / 接合段 | 40 次 / 13 段 |
| 段内间隔样本数 | 27 |
| 实际合并频率 | 10.376 Hz |
| 发送起点间隔中位 / P95 / 最大 | 55.809 / 232.128 / 253.554 ms |
| 透传 SDK 调用中位 / P95 / 最大 | 57.924 / 175.423 / 222.686 ms |
| 最短 SDK 调用 | 6.418 ms |

该轮存在后来已修正的循环累计落后误停，接合短、样本少，不能用来给当前透传定最终上限；也不能与后来的 Follow 当作严格同轨迹对照。但它足以说明当时没有实现 200 Hz。15:46 后续透传日志只有状态转换采样，26 个不同发送快照中还观察到 289.255 ms 调用；不能从这些快照计算完整吞吐率。

新增的确定证据是：**生产 SDK 的透传发送仍同步等待请求应答。** 静态核对实际绑定使用的 release 库并校验构建清单 SHA256，调用链为：

```text
robotServiceSetRobotPosData2Canbus(double*)
  → 本地 FK、组装单点 vector
  → RobotMoveService::setRobotPosData2Canbus(vector)
  → moveProfileAndWaypointsFormatCommunication
  → requestServiceOnlyCheckSendResultMode
  → sendRequestWaitResponse
```

`OnlyCheckSendResult` 这个名称不表示只写 socket 就立即返回。批量 vector 重载也经过相同请求应答层。它可以减少“每个点一次应答”的次数，但不会自动消除一次通信长尾。

当前 Python worker 每次等 SDK 返回后才能发下一次；同一个 owner 也负责串行停止。原生层释放 GIL 不会把 SDK 改成异步。透传还保留了串行状态查询；当前 CLI 只允许 Follow 使用 `--parallel-state-query`。因此直接切换模式也没有继承当前 Follow 的并行观测配置。

## 3. 抖动有哪些可证实的实现原因

当前 `follow.py::_cycle()` 在六轴模式下直接执行 `target = projected`，再调用 `send_joints()`。`native/follow.cpp::send_joints()` 校验时效、关节范围和许可，但没有对透传目标之间的速度、加速度或 jerk 作连续轨迹约束。

上游 IK 的单步位置变化有限制，默认 5 ms 一步、前三轴 150°/s、后三轴 180°/s，分别约 0.75° / 0.9° 每 IK 步。但 IK 持续更新，SDK 只取最新位置，中间未发送点被跳过。**IK 单步受限不等于相邻实际透传点受限，更不等于速度、加速度连续。** 当前核心 `observe()` 保留 IK 的命令 warm start，只更新实测状态；反馈到来不会每轮把命令重置成实测角。

本轮对上述 40 次发送重算：

| 相邻命令的最大单轴位置变化 | 中位 | P95 | 最大 |
| --- | ---: | ---: | ---: |
| 全部发送，含接合首点 | 0.575° | 2.081° | 2.486° |
| 每段首条发送，13 个样本 | 1.214° | 2.486° | 2.486° |

首条发送使用日志 `pre_send.previous_target_rad` 的起始目标作比较。首点前进入模式、状态查询与调度均可能占用时间，上层同时继续演进；现有路径没有保证“先提交与新实测角一致的保持点，再平滑进入运动”。

这些数字是**命令位置变化，不是机械臂实测速度或加速度**。当前柜端透传消费周期、插补、断流与缓存行为未完全核实，不能用角度除以 5 ms 宣称实体超速。但“稀疏且不均匀的发送 + 首点偏移 + 缺少执行层连续轨迹”是有代码与日志支持的抖动排查重点。没有证据把严重抖动简单归为手柄滤波不足，也没有同步关节高频实测足以证明其唯一根因。

不能假定 Follow 的运动规划与限速在透传下仍然适用；SDK 客户端速度参数也不是控制柜/驱动限速保证。

## 4. 厂家方案说明透传可用，但用法不同

本地厂家 Linux API 文本第 2.3.47–49 节和 SDK 头文件确认：进入、退出、六轴弧度单点及 `vector<wayPoint_S>` 多点发送接口均存在。教学示例每次仅加 `0.0001 rad`，调用后休眠 5 ms；“调用时间 + 5 ms”不是固定 200 Hz，示例也没有提供本机连续供点能力保证。

已保存的官方 ROS1 `AuboRobot/aubo_robot` 源码，提交 `32210c0b465bc4eef4de01a0917a878c3b24e799`，提供更接近轨迹执行的参照：

- `tryPopWaypoint()` 按 5 ms 计算相邻点速度，检测过大跨度并插入中间点，同时计算加速度；不能把其中全部检查描述为严格加速度限幅。
- `publishWaypointToRobot()` 读取 `macTargetPosDataSize`，按缓冲情况组装 vector 并发送多点。
- 其它轨迹路径包含位置/速度/加速度状态和 OTG 减速处理。

这证明透传有厂家轨迹执行用例，**不证明它天然适合零缓冲的最新位置遥操**。旧 API 文本将 `macTargetPosBufferSize` / `macTargetPosDataSize` 标作“预留”，官方旧驱动却使用后者；必须核实当前柜端该字段是否有效、单位及消费节拍，不能直接复制其常数或把 400 解读成 400 个六轴点。

参考源：[厂家 ROS1 驱动固定提交](https://github.com/AuboRobot/aubo_robot/blob/32210c0b465bc4eef4de01a0917a878c3b24e799/aubo_robot/aubo_driver/src/aubo_driver.cpp)。本地副本与来源指纹位于 `/data/robot_SDK/analysis/references/aubo_follow/`。

## 5. 与现有遥操核心兼容的目标结构

```text
Quest / 已验收映射 / IK → 最新期望关节目标
  → 透传执行层：首点对齐，保留 q/v/a 状态，在线生成连续轨迹
  → 单 owner 发送：按已核实消费周期送点、管理有限缓冲与撤销
  → 控制柜
实测反馈 / 状态 / 输入有效性 → 独立监测与停止协调
```

需要保留 world 映射、离合、实际反馈重新锚定与输入恢复规则。执行层从当前执行参考状态平滑朝新目标演进，限制速度、加速度，必要时限制 jerk；不是每来一个目标就从实测位置重新启动插值。实测反馈负责跟踪误差、边界和接合对齐；正常运行中如何校正参考状态需独立设计。

若稳定单点调用确实满足柜端允许周期，可走单点连续发送。若必须批量送点，应使用经确认的有限短时域缓冲，记录发送请求频率、点数、柜端消费率与目标响应延迟，不能把包频率当成伺服频率。

举例仅说明约束：假定已确认每点 5 ms，10 点对应 50 ms，20 次请求/秒平均可供 200 点/秒，**没有补充余量**；50 ms 缓冲也承受不了一次 230 ms 阻塞。要仅靠缓存覆盖 230 ms 就至少需要约 46 个未来点，并且恢复后供点能力必须高于消费率。这会增加目标改变和撤销的响应负担，不能用深队列掩盖通信问题。以上都不是已测柜端周期或建议缓存值。

Grip 释放后，已送入柜端的轨迹能否清除、退出模式是否中断或消费完剩余点、欠载如何减速、断网后如何停止，是批量方案的前置条件。当前“撤销 → 等在途 SDK 返回 → leave → slow stop → 新反馈确认”只覆盖现有实现，不能直接作为未来缓冲方案的停止证明。

现有产品功能也有边界：CLI 的 `--parallel-state-query`、录制 `--record` 及项目六轴归位路径目前限定 Follow；采用透传时需要分别补齐兼容和验证，不能仅替换启动参数。

## 6. 建议实施顺序与决策条件

1. **先处理机器人有线通信长尾。** 核对柜端速率/双工/自动协商，与电脑一致配置；换已知正常网线做单变量对照。继续对齐请求发出、响应到达/可交付、SDK 返回与回调，不把约 40 ms 一律归为 Python 或 delayed ACK。Quest 输入链路单独定位。
2. **向厂家确认当前柜端透传契约。** 提供实际柜端版本 `V4.5.111.71f2ee1-Alpha` 与 SDK 2.5.0，确认支持周期、推荐单点/多点方式、一次最大点数、缓存字段/单位、消费规律、欠载/溢出行为、退出与清空规则、断网停止保证。
3. **先做独立、有限的小幅平滑轨迹对照。** 隔离 Quest 输入与 IK，比较 Follow、透传的同轨迹结果，先建立与实测姿态一致的首点。测真实请求间隔及长尾、成功提交/消费点率、反馈误差、反向响应与正常停止。不把只读 getter 耗时当成透传性能，不运行带自动上电/归位的厂家示例。
4. **再实现并离线验证透传执行层。** 覆盖首点一致、限速/加速度/jerk、目标反向、慢 SDK、输入/反馈过期、有限队列、在途撤销及重新接合；不补跑旧手柄轨迹。通信契约与停止行为未清楚前，不启用多点预灌或改用多线程运动发送。
5. **通过有限实机验证后接回 Quest。** 按厂家支持范围逐级提高频率，比较相同动作的实际送点节拍、物理响应、抖动和异常停止，再做长时验收。200 Hz 必须同时有稳定供点和可接受响应证据；单看请求次数或 UI 参数不算通过。

若修复通信后单点透传仍明显慢于所需周期，而批量方式必须引入不可接受的延迟/停止距离，就不适合作为当前低延迟遥操基线。若短缓冲与在线轨迹在允许延迟下可持续供点，且停止可验证，则可保留现有高层核心、替换执行后端。

ARCS `servoJoint` 可另行作为厂家支持的伺服接口方向，但此前 `30004` / `30010` 拒绝连接。当前不能使用，也不能由此要求升级固件或认定硬件永久不支持。
