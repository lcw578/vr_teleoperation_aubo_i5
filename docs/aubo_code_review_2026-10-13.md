## 已复现的问题

### R1：会话时间戳解析异常没有撤销接合和目标

位置：`teleop/aubo/offline_session.py:98`、`:150`。

`float(received_monotonic_s)` 和 `float(generated_monotonic_s)` 在进入 `_fail()` 分支之前执行。传入 `None` 或无法转换的字符串会抛异常，绕过会话撤销。

假设备复现：有效反馈 → 松开/按下 Grip → 放入合法候选 → 将 input 或 offer 的时间戳置为 None。两种情况均得到 TypeError；随后 engaged=True、pending 仍存在、stop_requests=0；调用 dispatch() 仍可接受之前的目标。

这是离线状态逻辑的缺陷，尚未影响真实机械臂，因为该类强制只接受 FakePositionBackend。进入真机协调层前应处理时间戳转换异常，清除 pending、锁存故障并要求重新接合；补充测试应验证错误后的状态和后续提交，不能只验证抛出异常。

### R2：缓存自身的异常时间戳路径未统一失效处理

位置：`teleop/aubo/feedback.py:34`、`:47`。

缓存拒绝未来/乱序时间戳时抛异常，但保留原有 `_latest`。复现：有效反馈时间10.0 → 新反馈时间11.0且当前时间仍10.0 → ValueError → require_recent(0.1)仍取得旧的 valid=True 数据。

当前 `ReadOnlyFollower.query` 在缓存更新抛异常时会调用 invalidate，因此只读查询路径有额外保护。这一发现不能描述为“当前只读入口已在错误后读取旧反馈”。缺口是直接使用缓存的其他调用者必须自行处理，而未来持续反馈协调层尚不存在。

建议在缓存接口明确拒绝、保留较新有效样本和失效三种语义：未来/不可解析的主机时间应明确导致错误；合法较旧包可以按明确策略丢弃，不应把它覆盖成测量。调用者必须按故障规则处理，不可只捕获异常继续控制。需要覆盖缓存和会话组合测试。

### R3：查询后验证异常会丢失该次 SDK 原始结果

位置：`teleop/aubo/readonly.py:84`、`teleop/aubo/probe.py:31`。

如果 SDK 返回结果后，在反馈时间戳/结构处理阶段抛异常，`read_report` 只保存一个 return_code=None 的异常记录，丢掉已经取得的原始返回码、耗时和数据。

假 client 返回 rc=0、duration_s=0.001、未来主机时间11.0；实际报告只剩 ValueError，原始字段不在报告里。缓存已被只读层正确失效。

建议区分 SDK 原始结果与主机验证结果：保留原始返回码、数据和时间，附加 validation_error；无效测量禁止进入反馈，报告失败即可，不应通过删除证据实现失效。

### R4：仿真自动录制路径仍在主目录项目中

位置：`teleop/mujoco_session.py:406`。

不带路径的 --record 使用 ROOT/data/mujoco；此目录目前不是 /data 的软链接。这是旧代码已知现状，与未来录制实际存 /data 的偏好不一致。本轮没有更改或迁移它；Logger默认仍关闭，普通启动不落盘。

在修正自动路径前，如需录制，应显式指定已有 /data 目录下的新会话路径。新真机录制必须直接使用 /data，不能沿用这个默认路径。

## 真机接入前的关键缺口

1. **发送/反馈/停止没有形成真实闭环。** `ReadOnlyFollower.send_action` 和 stop 都直接拒绝；假 session 没有后台 watchdog，check()需要调用者触发。测试中的 stop_requests 只说明调用了假停止，不能证明停止机械臂。SDK 阻塞、线程卡住、停止失败、在途目标到达等场景尚未有集成演练。
2. **反馈年龄的含义有限。** 绑定记录的是 Get 调用返回附近的主机单调时间；没有控制柜采样时间。更新这个时间不能证明控制器产生了新测量。推送回调和通信/设备事件需明确实现与验证，不把高频查询叫作高频测量。
3. **不能把六个 SDK 值直接交给 core.observe。** 完整 RG 模型含额外夹爪关节，必须只映射前六臂关节，并区分夹爪测量和显示占位。模型 FK与SDK FK的基座、零位、法兰、TCP一致性尚未有接机结果；当前探测只收集SDK FK，没有自动模型对照工具。
4. **仿真恢复语义不能直接用于真机。** core对短暂输入超时保留自动重新锚定路径，符合现有仿真基线。真机需外部故障锁存、反馈有效性门控和真实按钮重新接合；只增加缓存不够。
5. **归位来源需门控。** 作者启动 ramp和摇杆归位绕过 solve()单步上限。首次真机不自动执行归位；后续开放时，所有目标来源都须通过发送检查和实测到位判断，不将仿真RG_READY自动下发。
6. **夹爪存在退出副作用。** 旧 RS-485 disconnect会禁用扭矩；close只关串口。已成功部署不等于适合采集退出。扭矩行为待用户/设备确认；首次连接不得因为默认 gripper状态而自动开爪。
7. **现有LeRobot facade仍默认构建DK1模型。** SingleArm只是选择输出手臂，BiQuest构造core时未注入AUBO模型。需要后续薄接口复用同一AUBO core/follower，并避免采集帧率成为第二个IK推进频率。

这些是已知的未实现项，不是现场一定会发生的故障。保持只读默认是合理边界，但不能据此宣布所有离线接口都完成。

## 接下来如何推进

现在可准备设备接线、查控制柜/固件信息，并执行显式只读探测。先取得实际地址、SDK端口、账户和只读状态信息，不运行旧motion_service来代替只读探测，因为其启动会初始化运动配置。

必须取得设备资料/实测证据的项目：跟随目标覆盖或积压、支持更新周期和实际耗时、可靠停止与断网行为、SDK并发规则、关节范围/方向/TCP/负载和夹爪退出扭矩。不能通过增加假测试来宣布这些完成。

保留用户认可的顺序：只读核对 → 无Quest跟随/停止验证 → 接Quest并验收故障恢复 → RG夹爪 → 相机/LeRobot。无需重写作者IK，也不能跳过后端工作。
