# Follow 请求 200 Hz 的现场手感与提交频率测试

用户在完成 50 Hz 请求试验后，授权改为 200 Hz 再测一次。仍使用六轴 `follow`、waypoint 反馈、world 映射和不主动写 SDK profile 的策略；默认正式基线保持 20 Hz。没有切换透传。

新增允许 `--follow-hz 200`，Python 与原生 prepare 均报告 5 ms 请求周期并核对一致性。SDK 调用仍串行，不补发旧点；原有输入、反馈、停止和故障保护保留。200 Hz 试验开启诊断时，worker 环形事件容量由 20000 增至 100000，以覆盖本轮 120 秒内可能出现的更高事件率。状态实时统计增加超过所选周期及两倍周期的间隔计数。

启动前构建、完整离线检查均通过：266 项 Python 测试，另有原生 fake SDK 和绑定离线检查。覆盖 5 ms 调度、慢 SDK 返回后不突发补发、200 Hz Follow/native profile 一致性、未连接拒绝和默认 20 Hz 保留。日志分别为 `/data/VR_teleoperation_runtime/aubo-follow200-build-20261028.log` 和 `aubo-follow200-check-20261028.log`。

本轮启动命令：

```bash

  --execute-six-axis --command-mode follow --follow-hz 200 --waypoint-feedback \
  --host 192.168.1.5 --port 8899 --user aubo \
  --rotation world --duration 120 \
  --diagnostic-output /data/VR_teleoperation_runtime/aubo-follow200-20261028-191421/diagnostic.jsonl
```

用户在桌面终端输入 SDK 密码，密码不写入脚本、聊天或日志。本轮约 19:14:25 就绪，计划 19:16:25 结束。独立监测只读本地 HTTP 状态，不创建另一 SDK 连接。完整诊断、监测采样和终端输出实际保存于 `/data/VR_teleoperation_runtime/aubo-follow200-20261028-191421/`。

比较口径沿用上一轮：按每个接合段内相邻 SDK 开始时刻计算频率，排除释放和 idle 时间；SDK 成功表示请求返回接受，不表示机械臂到位。测试手部轨迹未固定，因此两轮可比较提交节拍和调用分布，不能视为严格相同轨迹的物理响应对照或柜端极限认证。

## 实测结果

本轮于 19:16:25 按 120 秒时限结束。共调用 Follow 1749 次，全部返回接受；20 个接合段内得到 1729 个发送间隔，累计跨度 77.021670 秒，实际提交频率为 **22.4482 Hz**。完整诊断没有丢失事件，最终状态为 idle，`stop_confirmed=true`、`fatal=false`、`stop_result_unknown=false`。程序已退出，8443 端口已释放。

| --- | ---: | ---: |
| 接合期间实际提交频率 | 22.04 Hz | 22.45 Hz |
| 相邻 SDK 调用开始间隔：平均 | 45.38 ms | 44.55 ms |

频率只增加约 1.86%，无法据此认为提升请求频率带来了有效改善。本轮间隔超过 50 ms 的有 1047/1729（60.56%），超过 100 ms 的有 189/1729（10.93%）；上一轮分别为 38.24% 和 4.97%。由于两轮轨迹、接合时长和柜端状态未严格固定，不能将分布差异直接归因于频率设置。

在 77.021670 秒的接合段间隔中，前一次 Follow 调用占 63.994609 秒（83.09%），串行主动状态查询占 12.882577 秒（16.73%），其余仅 0.144484 秒（0.19%）。含主动查询的 529 个间隔平均 79.39 ms，不含查询的 1200 个间隔平均 29.19 ms。5 ms 请求调度几乎没有剩余等待空间，主要时间已被 SDK 请求/应答及串行查询占满。即使不计查询，平均单次 Follow 调用也明显超过 5 ms。

本轮候选目标在 SDK 开始时的年龄平均 2.42 ms、P95 4.46 ms，控制循环 `runtime_step` 最大 1.19 ms、无超过 100 ms 的循环停顿记录。这些指标支持优先检查 SDK/通信/查询路径，而不是继续单纯提高主机请求频率。反馈回调间隔平均 30.64 ms，约 32.6 Hz，同样不代表柜端内部伺服周期。

## 停止与收尾

记录到 19 次 Grip 释放停止和 1 次 `candidate_timeout`。这次超时发生在 **120 秒到时、Quest interface closed 之后的收尾阶段**：相邻 Grip 日志的墙钟与单调时钟对应关系将 interface closed 对应到约 5183.65 秒，超时请求为 5183.759323 秒，约晚 0.11 秒。当时候选年龄 108.36 ms，仍在进行状态查询。它应作为关闭过程中候选停止更新而触发的保护记录保留，不能描述为全程无超时，也没有证据将其归类为测试中途的控制柜故障。

20 次停止的慢停 SDK 调用平均 1014.15 ms、最大 1299.42 ms；停止请求到反馈确认平均 1277.38 ms、最大 1603.05 ms。该时间属于停止/恢复手感，与运动过程的目标发送周期分别统计。

## 结论与数据

当前六轴 Follow 链路将请求从 50 Hz 提至 200 Hz 后，实测仍约 22 Hz。这个结果描述的是当前 SDK、通信和查询策略共同作用下的主机提交吞吐，**不能证明控制柜硬件最高只能接收 22 Hz，也不能证明柜端收到并执行了 200 Hz 目标**。下一步应定位单次 Follow 请求/应答的几十毫秒等待来源，并评估主动状态查询的耗时及调度；涉及通信策略或接口模式的改动需要独立验证。
