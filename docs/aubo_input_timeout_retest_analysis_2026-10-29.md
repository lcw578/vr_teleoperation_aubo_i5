## 已排查的代码边界

六次故障时反馈缓存读取只有约 4.3～7.0 微秒。原生推送回调写缓存不获取运动 I/O 锁，也不需要 Python GIL；发送网络调用会释放 GIL。分析开始时的控制循环状态记录 `stalls=0`，最大整轮 work 约 6.76 ms，未见主控制循环 200 ms 停顿的证据。

全会话成功返回 Follow 共 4523 次，超过 200 ms 的有 7 次，均为 225～233 ms；其中 6 次对应上述反馈停止，另外 1 次在调用中先收到 Grip 松开，于 16:21:32.698 正常请求停止。没有超过 500 ms 的调用。该统计并不证明所有慢调用都由同一个底层原因造成。

## 结论及边界

1 秒输入超时确已工作，但本轮主要停止由另一条独立的 200 ms 关节反馈新鲜度检查触发。单 SDK 串行模式同样复现，说明并行查询不是该现象发生的必要条件。

六次反馈空档与同步 Follow 应答延迟重叠，定位范围在控制柜返回数据、以太网/TCP 接收或 SDK 收包/派发路径。时间重叠不能单独证明 Follow 函数锁住回调。

此前 10:45:47 的独立抓包已确证同一控制柜 TCP 流内有字节缺口、SACK 及补齐后回调和 Follow 同时恢复，见 `docs/aubo_tcp_gap_diagnosis_2026-10-29.md`。本轮 225～233 ms 的共同延迟与该表现一致，但本轮没有同步抓包，不能将既有一次抓包的结论直接推广到本轮六次事件。

下一步应围绕一次反馈停止对齐 TCP 字节连续性、SDK 回调和 Follow 返回：若按序可交付的数据也有缺口，分析 TCP 接收／发送路径；若网络及时交付而回调停顿，再查 SDK 派发。扩大 Quest 输入阈值不能消除已经确认的反馈过期条件。此报告不据此扩大反馈阈值，也不作根因已修复的声明。
