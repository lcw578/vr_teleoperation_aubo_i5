# 实测定位：TCP 字节缺口导致关节反馈与 Follow 应答一起等待

本报告对应 2026-10-29 10:45:47 的 25 Hz 复现。已确定此次中断存在真实的 TCP 按序交付阻塞；具体缺失发生在控制柜发送、网线、网卡或驱动的哪一处，仍需对照验证。不能仅凭本次记录将所有历史中断归为同一原因。

## 本次结果

电脑与控制柜直连（用户确认）。A 连接 `192.168.1.100:58724 -> 192.168.1.5:8899` 同时承载 Follow 应答和关节推送；B 连接使用本地端口 58730，只查询状态。

在 A 的 TCP 流中，接收端缺少序号区间 `[1792033723,1792033805)`，共 82 字节，恰为一个命令 7 关节推送消息。稍后电脑收到了后续 606 字节，但仍缺前述 82 字节，明确发送了 SACK。缺口补齐后，累计 ACK 跳到 1792034411，SDK 几乎立即恢复回调并返回 Follow。

这证明反馈空档在主机 TCP 按序交付之前已经形成；本次无需假设 Python 缓存锁、GIL 或 SDK 自身派发暂停，便足以解释中断。SACK 证明是真实接收缺口，不能解释成抓包漏记。抓包内核丢包为 0。

## 物理链路发现与结论边界

只读查询本机网口得到：

- `enp3s0`，驱动 r8169；100 Mbps，**半双工**。
- 本机自动协商开启，支持并通告 100M 全双工及千兆全双工。
- 驱动报告的对端能力只有 `100baseT_Half`；未报告对端 Autoneg 能力。
- 本机当时的 RX/TX errors、CRC errors、dropped、collisions 等累计计数为 0。
- 故障时段没有内核 link down/up 记录；网口没有整条断开。

100 Mbps 带宽本身不构成本轮低流量的解释。半双工与对端协商情况需要优先核对，但尚未读取控制柜侧实际速率、双工及自动协商设置，不能直接宣布存在双工不匹配，也不能据此单边强制电脑全双工。本机错误计数为 0 也不能排除控制柜端丢失或链路问题。

已确定的是 TCP 字节缺口及其按序阻塞后果；缺口原始报文没有在主机抓包中出现。后续补到报文的表现符合丢失/延迟后补齐，但具体丢失位置、发送端重传定时器及控制柜端 TCP 状态仍未直接观测。
