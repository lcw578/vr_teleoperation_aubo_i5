## 3. 证据修正：40ms 应如何理解

旧方案和部署总结的“柜端固定 40ms 服务节拍”“已排除 Nagle/Delayed ACK”“只能找厂家”不再作为后续依据。相关历史数字仍可引用，但机制结论由本节更新。

本日对笔记本历史抓包 `link-before-20261101-095423.pcap` 的离线复核结果：

| 指标 | 结果 |
| --- | ---: |
| Follow 请求/应答配对 | 3334 次 |
| 40–60ms 慢应答 | 1659 次 |
| 慢应答中：电脑延迟 35–50ms 发纯 ACK，随后 <1ms 收到应答 | 1652 次，99.58% |
| 上述 ACK 等待中位数 | 40.44ms |
| ACK 到应答中位数 | 0.106ms |

主要观察是：柜端关节状态先到；电脑约 40ms 后确认这批字节；柜端随即发出包含运动应答的后续数据。**强烈支持电脑 Delayed ACK 与柜端 ACK 门控发送耦合，柜端 Nagle 为首要嫌疑。** 尚未直接观测柜端 socket 选项，尚未完成 QUICKACK 干预，不能宣称机制已最终证实或修复成功。

证据文件（笔记本）：

- `/data/VR_teleoperation_runtime/aubo_ack_reaudit_20261102.py`；
- `/data/VR_teleoperation_runtime/aubo_ack_reaudit_20261102.json`；
- 抓包 SHA256：`ff592cee1276b8275be7b7168268dae1fdb16e43f7dd39447492162d1caae22a`。

限制：复核脚本针对这份 classic PCAP，通过本地端口内命令 22 的 FIFO 配对分析；不是适用于任意网络的通用分析器。其结果针对笔记本旧链路，车载网卡、内核和连接状态需要重新取基线。

0.08ms 表示本次 SDK 调用开始到请求上网线，不能解释成上一次应答到下一次请求仅隔 0.08ms。SDK 应答时间也不能直接等同手部动作到实体响应的延迟。

## 4. 任务一：左 Y 一键归位稳定性

### 4.1 当前归位到底怎样执行

源码依据：`home.py`、`quest_follow.py`、`follow.py`、`native/follow.cpp`。

```text
左 Y 新按下
  → 撤销遥操发送、请求停止并暂停录制
  → 确认停稳，读取实测关节角
  → 产生到已保存 home 的关节参考
  → 发送线程按步长/速度/加速度约束推进参考
  → 每点调用 Follow，同步等待应答
  → 目标附近用新反馈持续确认
  → 请求慢停，再确认实际停稳
  → complete，等待操作者重新接合遥操
```

当前关键参数：参考速度上限 20°/s、参考加速度 6°/s²、目标—反馈跟踪阈值 8°、最终关节误差容差 0.15°、到位观察时间至少约 0.15s、归位超时 180s。生成步长 `dt` 使用实际发送间隔并封顶为 3 倍请求周期，25Hz 时为 0.12s。

这些是主机算法约束，不是已经测得的实体峰值速度/加速度或停止距离。当前没有环境路径规划器；关节空间逐步回 home 不保证 TCP 走直线或绕开植株/收集框。

oneshot 忽略左 Y 松开；代码在 `moving` 状态下第二次新按下左 Y 会取消。等待停稳/准备等阶段的再次按键行为需要明确并补测，不能把“任意阶段第二次按键都会取消”当作现状。

代码还有文案不一致：部分状态提示和 `control_button` 仍写“按住”；manifest 的 oneshot 策略写 `grip_release_stops`，实际接收路径对 `_home_busy()` 有保护，右 Grip 不是归位持续许可。后续应按实测和明确的交互设计统一 HUD、元数据、帮助与测试，不能让操作者凭旧提示判断停止方式。

P1 可以先实现；P2 完成前不能宣称“番茄串自动放置已完成”。

### 5.2 徐灿的实现：已经从本地源码核实的事实

参考源码为 `/data/robot_ws_dev/src/xc_aubo_arm_control/src/motion_service.cpp`，本轮只读，没有运行该节点。

`handle_return_request_1()`（约 919 行起）读取 `midpoint_point_`、`from_mid2target_waypoints_`、`last_midpoint_contract_position_` 等上次采摘保存的上下文，按条件逆序经过已有路点，再到 `pick_start_position_` 和 `initial_position_`。

实际调用主要是 `robotServiceJointMove(..., true)`。即使注释写“直线”，也不能据此当作 `robotServiceLineMove`；要以调用函数为准。它还使用提前到位设置和固定关节姿态，不能直接复制到当前装配。

`auboi5_path_check.cpp` 使用 Bullet，包含关节限制、自碰撞和两个固定箱形障碍物检查。检查对象是传入的离散轨迹点，没有据此证明点间柜端实际轨迹的连续碰撞覆盖；也没有证明覆盖植株、当前蓝框、夹持的番茄串及线缆。URDF 路径和部分几何硬编码在旧部署位置。

由此得到三个设计边界：

1. 柜端 JointMove 能承担点间运动生成，但不等于自动识别环境并规划避障。
2. 徐灿的返回服务依赖他的前向采摘上下文。我们的遥操任意起点没有自动生成这些历史点，不能直接调用旧服务获得等价行为。
3. “从当前位置”先实现为从经确认的采摘工作区/姿态集合出发。任意可达姿态的一键绕障返回是更大的规划问题，不在首版默认承诺范围内。

### 5.3 运动后端选择建议

区分两个独立决定：**谁拥有运动控制权**，以及**用什么接口执行路径**。建议保持现有进程内唯一运动 owner；这个 owner 可以顺序调用 Follow 或柜端点到点接口，不要求所有功能使用同一种运动接口。

| 路线 | 用法 | 优势 | 需要补齐 | 初步位置 |
| --- | --- | --- | --- | --- |
| 同一 owner 调用柜端 JointMove/LineMove | 主机给经检查的过渡点，柜端生成点间轨迹 | 固定目标搬运不必连续 25Hz 喂点；与徐灿经验接近 | 模式交接、可中止、到位确认、profile 恢复、路径检查 | **优先评估用于左 X；通过后再评估左 Y 是否复用** |
| 现有 Follow 扩展多路点 | 主机生成连续参考并跟踪反馈 | 复用现有诊断与撤销机制 | 多段路径/笛卡尔段、持续供点与跟踪 | 停止/接口契约不满足时的备选 |
| 调用徐灿 ROS 服务 | 遥操让出控制后由其节点执行 | 可复用已部署功能 | 上下文适配、进程互斥、控制权交接及状态回传 | 确认现场服务可复用后再选，不直接开第二路运动发送 |

SDK 头文件提供 `IsBolck=false` 的非阻塞点到点选项。它表示不等待到位，并不保证网络调用绝不阻塞。优先研究“短调用提交 + 后台实测监控 + 可停止”的方式，不能把徐灿的 `true` 阻塞调用直接塞进当前占锁 owner，让其在长行程期间无法处理取消。

通信调用预算和整段运动完成预算应分开。当前流式发送的 500ms 预算不宜直接当作几秒搬运的完成期限。

### 5.4 路径与配置

首版按徐灿部署与现场几何定义：当前采摘点 → 经验证的退出/退让点 → 跨区过渡点 → 蓝框上方放置点。**退出方向需要按作物和夹爪姿态确定，不预设为全局 Z 向上。** 是否增加下降段由容器和释放高度决定。

点位配置建议独立于 `aubo_home` 保存：实测关节角、必要的法兰/TCP 位姿、坐标系、工具版本/偏移、负载、相机/蓝框和机械臂基座安装条件、允许起点范围、各段类型/速度/加速度、到位容差、版本与示教日期。车载保存于 `~/code/lcw/VR_teleoperation_runtime/config/`。

关节段不保证末端直线；需要保持退出方向/末端姿态的段再评估 LineMove 或经过 IK/路径检查的笛卡尔参考。全路径考虑机械臂、夹爪、夹持物尺寸及固定障碍物，不把果实当质点。

### 5.5 按键、门控与状态机

建议状态流程：

```text
idle → requested → stopping_teleop → checking
     → retreating → transferring → arriving
     → verifying_arrival → releasing → verifying_release → complete
任一运动阶段 → cancelling → stopping → cancelled
任一异常 → stopping/fault；结果未知则锁定
```

左 X 是新按下沿触发；持续按住不重复提交。第二次按左 X 建议作为取消，覆盖等待/准备/运动阶段；释放命令已发出后无法“撤销已发生的释放”，状态机必须准确报告当前阶段。X/Y 同时请求不能排队执行第二条自动运动，建议拒绝冲突并要求重新按键。

前置门控：有效点位与路径、允许起点、无故障/未知停止、反馈新鲜、现有运动已停稳、工具与负载匹配，以及成功分离且稳固夹持的确认。

首版真实搬运建议使用独立明确的人工确认（网页确认/状态项），后续再加入夹爪位置、电流或其他反馈。**夹爪闭合只能部分证明夹持，不能自动证明果柄已分离；右 Grip 是现有遥操离合，不直接复用成隐式“采摘成功”确认。** 确认应绑定本次采摘周期，在使用、取消、故障或换段后失效。

到位确认使用实测位置/关节误差与稳定反馈，不以 SDK 返回 0 替代。放置点确认停稳前不释放；释放失败不宣布完成，保持可诊断状态。取消、故障或断流不自动张爪。

自动运动期间的输入丢失/头显退出策略应明确设计并测试；不能复制 oneshot 的“忽略 200ms 管理按键空档”就推导为无限失联仍可运行。软件取消、输入监测和现场停止方式各自保留可验证的作用。

### 5.6 录制语义需要一并设计

当前导出器仅接受 `control_source=teleop`，归位会暂停有效采样。直接复用归位代码可能让 Placement 被导出全部排除，不能实现后再补解释。

建议新增 `control_source=placement` 与请求、段开始/完成、到位、释放请求/反馈、取消和失败事件，保留其实际 SDK 请求/返回及关节观测。Grip 暂停和自动动作的生命周期应分开，自动搬运无需按住 Grip 时不能每帧又被判作普通遥操暂停。

若使用柜端 P2P，一条目标触发整段运动，不能把最终蓝框目标复制成全程 25fps 的逐点伺服 action 并声称等价。先记录原始事实；策略是否学习放置、P2P 阶段采用何种训练动作表达另作明确决策。首版允许将脚本化 Placement 排除于模仿学习样本，但保留原始事件与观测。

## 6. 任务三：降低遥操延迟、选择合适控制方式

### 6.1 先拆开四类时间

| 时间 | 测量办法 | 不应混用的量 |
| --- | --- | --- |
| 输入进入主机到候选生成 | XR seq/接收时间 → 主循环消费 → candidate | 200Hz IK 不代表 200Hz 新输入 |
| 候选等待发送 | 实际提交机会与目标更新时间 | 被挑中的 candidate 很新，不代表手部变化没有等发送机会 |
| SDK 请求/应答 | 调用开始/返回、线侧请求/应答、TCP ACK | 不是实体运动到位耗时 |
| 目标变化到实体响应 | 小幅可重复轨迹、实测关节曲线，必要时外部视频 | 反馈到达时间带有采样和传输不确定性 |

### 6.2 L-1：车载现状取基线

首先在车载同一套 USB/Follow25/串行查询配置上取短时基线，记录 SDK 时长分布、真实提交间隔、状态查询耗时、关节推送间隔/年龄、取消到停止调用及确认的时间，并抓取同一会话流量。

运动实验以停止路径核查结果为前提；ACK 特征可先在只读推送/查询链路观察，能否复现运动应答慢峰需后续同协议对照。只读 getter 提速不能替代运动接口提速的证据。

### 6.3 L-2：有开关的 QUICKACK A/B

仅调整目标柜端连接的 ACK 策略，先维持运动接口、25Hz、状态查询、速度和输入一致。可以研究精确定位 8899 socket 的预加载包装或显式传输适配，但先离线验证拦截范围、递归/多线程处理、失败返回和日志；不全局修改 TCP sysctl。

注意三点：

- `TCP_QUICKACK` 是临时提示，需核实实际 `recv`/`recvmsg`/`read` 路径及调用时机；每次 setsockopt 返回值可追溯。
- 电脑端 `TCP_NODELAY` 只控制电脑发包，不能关闭柜端 Nagle；如需试验应与 QUICKACK 分开，避免分不清哪个因素起作用。
- 关闭开关重启实验连接即可退回原配置；不把“预加载成功”当作“选项已作用于正确 fd”。

建议 A（基线）→ B（QUICKACK）→ A（回退）同协议对照。最有价值的判据是抓包中“状态推送后约 40ms 才 ACK”的比例显著下降，且随 ACK 紧跟应答的慢峰同步收缩。

初步目标可设：慢峰比例由本机基线显著下降（例如降至 <5%）并在重复轮次出现，SDK P95 改善且无新增长尾/停止异常。目标未达到时报告实际分布，不为满足目标删样本；小样本不能证明长时稳定。

### 6.4 L-3：先判断是否还需要提频或分离查询

ACK 改善不等于请求率提高：25Hz 仍受 40ms 主机发送周期限制，状态查询也占用串行 owner。先在 25Hz 下观察稳定性与手感，再根据同条件证据考虑独立状态观测或更高请求率，一次只改变一个因素。

现有 CLI 支持 Follow 20/25/50/200Hz；不把未实现的频率档位写成可直接执行命令。若需更高频，先检查原生/Python profile 一致性、主机步长与滤波时间尺度、柜端允许周期和实际停止表现，不能直接跳到 200Hz。

关节推送不一定能替代运行状态/故障状态查询；不能为了去锁争用把独立保护信息直接删掉。两条连接也不保证柜内资源独立。

### 6.5 L-4：在同轨迹比较后选遥操后端

| 方式 | 适合什么 | 本项目现状 | 进入下一步的条件 |
| --- | --- | --- | --- |
| Follow，先修 TCP 再评估节拍 | 连续遥操目标 | 当前已实跑基线 | 首选验证，若实际响应达标则保留 |
| TCP→CAN 透传 + 在线轨迹生成 | 高频连续参考 | 已有进入/发送/退出实现；早期单点仍同步等待，未达 200Hz | 确认消费周期、短缓冲、欠载和退出/清空/停止；同轨迹证明收益 |
| 柜端 JointMove/LineMove | 归位、放置等固定终点 | 徐灿代码有先例，本链尚未集成 | 不作为连续手柄每帧运动的替代；可独立用于自动动作 |
| ARCS/其他厂家接口 | 厂家支持的伺服接口 | 既有端口拒绝连接，兼容性未确认 | 现有路径不能满足需求或厂家给出明确支持时再推进 |

10 月 28 日透传单点试验：40 次成功发送，调用中位 57.9ms，最小约 6.42ms；SDK 静态调用链仍到 `sendRequestWaitResponse`。样本少且有旧调度问题，不能判其最终上限，但能否定“换函数就已达到 200Hz”。

若评估透传，轨迹层至少需要实测首点衔接、参考 q/v/a 连续推进、实际发送跨度约束、最新目标更新、有限缓冲、停止撤销和重新接合；不是对不均匀旧点补发，也不是加一个滤波器即可宣布平顺。

### 6.6 最终以实体响应验收

先做固定的小幅往复参考，比较目标、反馈与方向反转，再接手柄主观试用。给出源时间、参考/命令时刻、反馈接收时刻及采样分辨率，避免通过任意平移曲线掩盖延迟。

不提前承诺手到臂 <某个毫秒数。验收至少包括：同条件下可重复改善、无新增积压、反转不追旧目标、停止/恢复不退化、录制负载下仍保持既定采样质量。相机显示链路的视觉延迟另测，不能把所有“感觉慢”都算到命令应答。
