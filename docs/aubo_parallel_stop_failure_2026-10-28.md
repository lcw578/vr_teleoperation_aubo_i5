## 已确认的实现缺陷与证据边界

旧 `validate_state_result` 将非零 SDK 返回码和状态值不属于 0/1 合并为同一错误。`StateQueryWorker` 发生该错误后使缓存失效并永久结束查询，停止确认随后无法继续取得观测。即使出错原因只是 SDK 定义的暂停=2、恢复=3，也会走同一路径。

供应商 `AuboRobotMetaType.h` 明确定义运行状态 0=停止、1=运行、2=暂停、3=恢复。旧实现错误地将“成功观察到已知但不允许运动的状态”与“通信/观测失败”混为一谈。此前离线测试只检查暂停时拒绝发送，没有检查在慢停期间观察到暂停/恢复后应继续查询的情形，这是测试覆盖缺口。

原始现场失败查询没有开启完整诊断，而且旧代码在验证成功后才记录结果；fatal 日志也没有包含 B 的最后原始查询。因此**无法从这份日志判定失败查询究竟是非零返回码、2/3 状态还是未知状态**。不能将上述可复现缺陷描述为已经证实的现场唯一根因，也不能据此断言双连接不兼容。

## 本次修正

1. Python 验证和原生缓存均允许 0–3 作为有效观测，但原生 arm 仍要求 0，运动发送仍只允许 0/1；2/3 不扩大运动权限。
2. 并行模式的停止确认允许观察 2/3 并继续等待；只允许 0 加停止后新查询、真实关节反馈至少跨越 100 ms 的静止窗口确认停稳。状态/关节 200 ms 时效和原停止截止时间均保持。
3. 真正 SDK 返回失败、未知状态、过期与超时仍使观测失效并撤销发送许可，没有添加自动重连或串行降级。
4. 每次 B 查询在验证之前保存 `last_attempt` 并记录原始结果；失败原因区分 `state_query_failed` 和 `state_query_unknown_state`，包含 `rc`、`state`。
5. 首次停止/严重故障事件包含 B 的最近有效结果、原始尝试和在途操作。原生缓存错误包含状态、返回码、有效性与关节/状态年龄，便于下次从普通终端日志判定。
