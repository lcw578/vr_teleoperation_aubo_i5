# 启动后无法控制：串行快照旧关节样本误锁定

日期：2026-11-02。发生在左 X 空载路线的篮筐点示教准备阶段。

## 现场事实

会话 `home-field-20261102-164312-kmLSCS` 启动后即锁定为 `RuntimeError: feedback_reception_expired`。USB 设备在线、`adb reverse tcp:8443` 存在，网页服务和头显连接均正常。`hardware.submitted=0`、`last_attempt=null`、`last_stop=null`、原位状态 idle，说明该会话尚未下发运动或执行归位。故障发生时 `input_age_s=null`，早于首次有效遥操输入，不能归因于后续摘下头显出现的右手柄缺失。

关键车载单调时钟记录：

| 记录 | 时间/结果 |
| --- | --- |
| 串行 snapshot 调用开始 | 7589.618228444 s |
| 返回的关节样本接收时间 | 7589.602552738 s |
| 返回的运行状态接收时间 | 7589.623355329 s，状态 0 |
| snapshot 调用结束 | 7589.807136323 s，总耗时约 188.906 ms |
| 故障锁定 | 7589.807165620 s；旧关节年龄 204.613 ms，状态年龄 183.810 ms |
| 故障前已接收的新推送 | 序号 33，7589.781968373 s，年龄约 25.197 ms |

后续 `push_observed` 的增量 SDK 回调历史保存了上述新样本。因而这里不是已经证实的 204 ms 柜端推送中断，而是 snapshot 带出的关节样本在调用结束时变旧，检查时没有从独立推送缓存更新。读取耗时包含网络请求和主机调度；现有证据不能把 188.906 ms 全部归因于网络或柜端。

旧 `_run` 把此异常按致命故障锁定，之后虽然关节推送仍然正常，Grip 也无法恢复。该问题与前面已修复的停止 SDK 锁顺序 `10007` 不同；本轮没有停止调用或 `10007`。

## 最小修复

只调整 `follow.py` 的普通串行观测：若关节样本年龄超过 200 ms、控制柜状态仍在 200 ms 内，且已启用独立 waypoint 推送读取，则从 SDK 已接收的内存缓存读取一次最新实际关节样本，随后重新执行两类反馈的原有时效检查。

不增加 SDK 查询，不把主机检查时间伪装成接收时间，不提高 200 ms 上限。旧样本先保留合法性/关节范围检查；刷新使用推送本身的真实接收时间、序号和关节值。状态反馈不会被关节推送刷新；读取后状态过期仍拒绝。没有推送读取能力、推送确实过期、未来时间、越界/无效数据、错误状态、超预算仍拒绝。

快照保存 `snapshot_joints_before_refresh`，诊断增加 `serial_snapshot_joint_refresh`，以区分初始关节样本和真正采用的新推送。停止确认、并行观测、输入超时、运动参数以及已修复的停止适配器未改变。

## 验证与现场后续

新增 9 项合成时序测试，复现上述 204.613/183.810/25.197 ms 组合，并验证真实旧推送、旧状态、未来关节时间、无推送读取能力、越界与错误状态、读取中状态变旧均不能授权控制；新鲜快照不增加推送读取，停止确认保留原检查路径。

修复后本地 230 项定向离线回归通过，覆盖 Follow、六轴、归位、录制、状态查询、新时序和示教工具。车载部署和回归结果见运行目录中的本次部署清单。

已保存故障状态并对只发送过 0 条运动命令、SDK 无在途调用的已锁定进程发送 SIGINT，进程正常退出，`field-result.json` 的 `session_exit_code=0`；抓包内核丢弃计数为 0。原现场目录和录制保留，本地副本位于 `/data/VR_teleoperation_runtime/placement-20261102/idle-snapshot-stale/`。

部署后需要操作者使用原启动命令重新启动。先保持 Grip 松开，核对 idle、`fatal=false` 和新鲜反馈，再唤醒手柄做小幅接管/松开验证；验证成功后继续篮筐上方点示教。离线通过不写成现场已经恢复，不以清除故障锁存或强制继续旧进程代替重启验证。
