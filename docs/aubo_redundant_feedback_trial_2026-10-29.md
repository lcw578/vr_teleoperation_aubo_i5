| 11:37:13.319 | 206.95 ms | 3.49 ms |

| 11:38:52.635 | 205.86 ms | 11.74 ms |

| 11:39:18.069 | 200.45 ms | 4.17 ms |

这些停止发生时 Grip=true、输入有效，查询 B 正在等待响应。关节反馈可由 A 保持新鲜，但它不能替代运行状态数据。

旧调度在状态查询返回后等待 100 ms，再发下一次查询，所以实际状态更新间隔是 `100 ms + 下一次调用耗时`。例如第一次旧状态在 11:37:13.112 返回，下一次 11:37:13.212 开始、11:37:13.484 才返回，中间缓存超过 200 ms，11:37:13.319 触发停止。

修正为开始到开始的周期：活动 100 ms，idle/停止 50 ms。每次调用占用本周期，超过周期则返回后继续下一次，只有一个在途调用、不追赶补发。该修改去除额外等待；单次调用仍可能超过 200 ms，因此不能承诺仅靠调度就消除状态过期。

## 两次主机控制循环停顿

11:37:48.184 与 11:38:48.475 由候选目标超过 100 ms 未更新触发。控制循环的反馈刷新分别耗时约 96.4 / 117.4 ms，完整循环约 100.2 / 121.5 ms；原生缓存读取本身仅约 0.096 / 0.077 ms。因此不能将它们直接归为 IK 算慢或缓存锁等待网络。

旧诊断历史保留 100000 条含嵌套字典/列表的 Python 事件，并在每个 5 ms 控制周期把原生最多 256 帧重复转换为 Python 对象，带来大量分配与对象扫描。离线加载相同事件后，完整垃圾回收扫描三次约 114.7、97.7、111.3 ms；缩小到 4096 条后约 3.9、1.2、1.0 ms。这是与现场停顿吻合的可复现开销来源，但旧记录没有 GC 起止事件，不能据此确认这两次现场停顿均由 GC 引起。

修改如下：

1. 流式诊断只保留 4096 条内存历史；8192 条有界待写队列和持续文件输出保留，覆盖数继续显式报告。
2. `waypoint_feedback_since(sequence)` 仅转换新增回调；没有新增回调时返回原最后一帧，保留旧时间戳，让过期检查继续生效。
3. 增加低开销 `python_gc_pause` 诊断，记录至少 5 ms 的 GC 扫描，供下一轮与主循环停顿对时。回调内不写文件、不调用 SDK、不获取运动锁。

假 SDK 的 10000 次缓存读取对照：旧完整读取中位 66.5 微秒 / P99 112.5 微秒，增量无新增帧中位 1.19 微秒 / P99 1.28 微秒。该对照不代表真机端到端提速。
