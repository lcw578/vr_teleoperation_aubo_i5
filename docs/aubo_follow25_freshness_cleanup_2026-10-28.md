# 25Hz Follow 与观测过期处理清理

用户要求核对所有时效来源、清理非必要冗余，并将本轮50Hz请求降为25Hz。仅把200ms改为300ms会延后触发，不能解决查询线程退出后停止确认失去观测的问题。本次保留200ms运动反馈时效，修正错误的故障分类。

## 当前时效清单

| 对象 | 数值 | 来源/用途 |
| --- | --- | --- |
| XR每只手输入、相对源时延 | 200ms | 仓库复用的vr-teleop-kit核心；失联脱开、旧输入不接合 |
| AUBO协调层输入 | 250ms | 后增；接收线程/硬件watchdog独立撤销，不依赖IK仍在运行 |
| IK候选目标 | 100ms | 后增；拒绝发送旧目标 |
| 实测关节、运行状态 | 200ms | 后增；Python与原生arm/send按真实接收时间检查 |
| 作者核心外层shadow关节反馈 | 250ms | 后增；候选层门控；真机发送采用更严格的200ms |
| 主控制循环真实停顿 | 100ms | 后增；撤销旧锚点/目标，不把单纯跳过时点当停顿 |
| 单次Follow/状态查询等SDK调用 | 500ms | 后增；返回异常或超时仍永久锁定，独立watchdog处理在途阻塞 |
| 运动发送长间断 | 650ms | 后增；停止并要求新释放/按下，不补发旧点 |
| 慢停完成 | 2s | 后增；单独预算，不以500ms运动调用标准误判慢停 |
| 慢停后的反馈确认 | 2s | 后增；超时停止未知，不冒充已停稳 |
| 静止窗口 | 至少100ms | 后增；实际新关节时间戳跨越窗口，非旧帧重复读取 |

25Hz发送周期为40ms；后台active查询仍为上次接收后100ms，idle/停止为50ms，作者IK期望200Hz。这些是调度周期，不是有效期。1s初始查询就绪及退出join等待属于生命周期边界，非运动目标有效期。

来源核对：`third_party/vr-teleop-kit/src/vr_teleop_kit/core/quest_teleop.py` 的XR_FRAME_STALE_TIMEOUT_S=.2在本仓库已提交基线HEAD中已经存在。本次没有修改该核心；这证明复用基线已有输入保护，不声称已核验所有规则的上游历史。AUBO专属状态、SDK、慢停预算均不是作者核心要求，也不是已获厂家保证的上限。

各层检查不能因数值相近就全部删除：作者核心保护输入语义；外层线程可在核心不运行时撤销；原生检查位于最终SDK发送入口。可删除的是重复分类、无效调度及把观测年龄混为连接错误的行为。

## 本次移除/调整

1. watchdog不再因state接收年龄超过200ms调用StateQueryWorker.fail。改为撤销运动许可、清空目标、请求停止，健康B通道继续观测。
2. A缓存快照的ObservationPending在运动阶段同样触发可恢复停止，不再被通用异常升级为fatal。真正未来/非有限时间戳仍失败。
3. Python检查后、原生发送前刚好过期的窗口：原生仍拒绝调用SDK，Python识别该明确时效拒绝并按同一可恢复停止处理；范围、未知状态等其它拒绝仍保持故障规则。
4. B线程不重复用接收年龄决定是否永久失败；成功但延迟处理的结果保留原时间戳，运动消费者仍按200ms拒绝。返回失败、未知状态、非法时间关系、500ms调用超时及代次失效规则保留，未允许被真正失效的代次复活。
5. 并行A循环不再计算不会采用的串行查询节拍。串行路径仍保留其必要调度，两者职责明确。
6. CLI、Python worker、C++构造、prepare周期校验完整支持显式25Hz=40ms。旧20Hz默认和显式50/200Hz选项保留，防止改动已有其它入口。当前用户试验配置使用25Hz。

没有把200ms放宽到300ms。若SDK/通信长尾持续触发200ms保护，仍可能停止，但不会仅因该短暂过期杀死健康查询线程。停止后必须取得慢停后开始的新查询、慢停后新关节、足够静止窗口；确认后需新鲜释放/按下，不能自动续跑旧目标。停止确认2s内始终无法获得证据、真实SDK超时等仍锁定。

## 验证

新增实际生产绑定+假SDK回归覆盖watchdog过期、快照过期、原生send临界过期三条路径：均不得发送旧目标，B存活，成功查询可继续用于确认，且确认只能使用停止后新查询；新接合可运行。500ms真实查询超时及迟到失效仍不恢复。原有未来时间戳、时间竞争、Grip严格恢复和停止期限测试保持。

新增25Hz节拍/无补发、prepare一致性、CLI双连接接线及原生构造检查；新增B成功结果处理延迟不杀线程但运动消费者拒绝旧时间戳检查。

正式绑定已重建，完整离线检查300项通过：277项Python单元、23项生产绑定假SDK集成，另有原生profile/透传、正式绑定未连接拒绝、默认入口与Shell检查。日志位于`/data/VR_teleoperation_runtime/aubo-follow25-recovery-build-20261028.log`和`aubo-follow25-recovery-check-20261028.log`。

此前已锁定的50Hz/30分钟会话以SIGINT正常收尾、两个接收线程退出后再构建，没有清锁或把已退出查询线程复活。修正后的25Hz尚待真机复测，不能将离线恢复验证描述为30分钟稳定性验收。

随后尝试启动25Hz/30分钟会话，双连接登录成功，但prepare以`invalid_sdk_client_profile`拒绝，未进入遥操。现场读回的六轴 SDK 客户端参数为明显异常的未初始化/不可靠值（约`10^247`、`0.0`等）。该路径只读取客户端内存，不是控制柜查询；六轴 Follow 也不写入或依赖这些参数，因此已移除六轴正常运行路径上的读回和拦截。显式`--inspect-profile`仍保留读回检查，旧 J6 路径仍保留设置后读回校验。日志：`/data/VR_teleoperation_runtime/follow25-stability-20261028-211558.log`。

修正后，六轴正常 prepare 的 profile 记录为`source=not_read_six_axis_unmodified`，速度/加速度数组为`null`，避免把垃圾内存解释成控制柜配置。正式绑定已重新构建，离线检查日志为`/data/VR_teleoperation_runtime/aubo-follow25-profile-fix-check-20261028.log`。
