# PE TCP2CAN 完整排查收敛记录

日期：2026-11-08。范围：复核已部署代码、历史遥操与保持记录、PE/官方驱动资料，并在车载电脑上完成四组有限、只读的真实控制柜对照。当前版本 `V4.5.111.71f2ee1-Alpha`，SDK `aubo_sdk-2.5.0-linux64.bf7070c`，库 SHA256 `a04ad0aa05b2d46fea5a863fe30698950e6434afeafd5a3eaf605c3f0df0ff1b`。没有进入透传、没有发送位置点、没有执行停止指令；本轮没有修改生产代码、网口、路由或保护阈值。历史受控保持的结果另行引用，不算本轮新增运动。

## 结论与处理优先级

1. **已经在真实控制柜上复现“异步关节推送开启后，同连接业务请求出现显著慢峰”。** 单连接 ABABA 切换中，关闭推送共 180 次状态查询，平均 8.773ms、P95 17.401ms；开启推送共 120 次，平均 22.941ms、P95 53.499ms。它不需要 VR、IK 或第二连接就能出现。这里测的是 `GetRobotCurrentState`，不是透传吞吐量，不能据此宣布完整遥操已修好或全部归因。
2. **链路存在当前发生的真实错误。** 双独立进程对照的约 16 秒内，eno1 新增 1 次 TX 错误、1 次碰撞；A 的一个 3 秒窗口中 TCP 累计重传从 0 增至 1，并出现 233.579ms 查询。之后只读驱动统计显示 `tx_abort_late_coll=1`、`tx_window_errors=1`。不能再把网口完全排除，也不能用这次重传倒推历史无重传窗口的所有慢峰。
3. **将运动连接与推送流量分开有实验依据，但还只是待验收的架构方向。** B 自己接收推送时，B 的两段查询平均 31.513/37.541ms；A 不接收推送时，大多数查询仍较快。存在新重传和少量 A 长尾，不能声称跨连接完全隔离；更没有运行此架构的透传保持。
4. **真实下发轨迹缺少速度/加速度连续性约束的缺口仍存在。** 位置 EMA 不是轨迹生成器，查询/网络长空档也不能靠它消除。通信交互与执行轨迹应分别修复；当前证据不能唯一确认机械异响就是某个加速度或碰撞算法引起。
5. **ACK 后约 182ms 的柜端内部环节、消费/缓存/停止规则仍未查明。** 已把主机能证实的外部边界固定；柜端内部日志/受支持诊断入口不可用，公开资料也没有覆盖所需契约。到此不再以重复保持或猜测“三帧缓存”代替内部证据。

优先处理顺序是：核实/修复有线两端配置及物理链路 → 按下述分工准备反馈与运动连接 → 在 PE 明确规则内补齐轨迹连续性和停止 → 有限保持通过后再进行小幅运动/VR验收。不是先关闭状态保护、放宽 200ms、再看能跑多快。

## 1. 当前部署究竟在做什么

已核对车载与本地 `native/follow.cpp`、`process_state.py`、`state_query.py`、`follow.py`、`aubo_passthrough.sh` 的内容哈希一致。

- 当前是 **PE TCP 转 CAN 透传**：Enter/SetRobotPosData2Canbus/Leave。这里的“CAN 透传”“TCP2CAN”“透传”是当前同一调用路径，不是 PC 串口直接写裸 CAN；不能理解为无业务处理、无缓存或无等待。
- 实际关节角在初始化注册 `RealTimeRoadPointCallback`，回调 `wayPoint_S.jointpos` 写入缓存并保存原接收时间。不是在发送循环里每帧 GetJointStatus/GetCurrentWaypoint。
- B 独立解释器持有独立 SDK，仅主动查完整 `RobotState`。活动目标周期 100ms，空闲 50ms；不是 200Hz 高频查 IO。A 只读原生缓存；IPC 接收不会刷新观察时间。
- 回调是异步交付，不表示它与业务响应在网络/SDK 接收路径上独立。SDK 静态核查显示同一接收分发路径处理推送与业务响应；RoadPoint 在 SDK 中还会先解析关节角、调用 FK，再回调应用。应用回调本身只复制/缓存，不调用 SDK。
- 注册 RoadPoint 回调会自动启用推送；不能只看有没有显式调用 `SetRealTimeRoadPointPush(true)` 判断订阅状态。诊断程序的关闭阶段是在注册后显式关闭，并以实际回调数 0 验证。
- 目前只在 A 订阅关节推送；B 的重复推送已关闭。此前进程隔离已经实施，但保持仍失败，因此“同进程某一把 SDK 锁”不能当作必要原因。
- 公开关节/路点回调不包含完整 RobotState；事件也不是经确认的周期完整状态快照。因此不能直接删掉 B 查询后声称原保护等价保留。

## 2. 新增四组只读真实控制柜实验

所有查询均返回成功且 `RobotState=0`（Stopped）；本轮各会话均正常注销。查询周期指测试请求的目标节拍，不是实际伺服/透传频率。所有百分位由 `analyze_readonly.py` 以 `(n-1)*p` 线性插值统一重算。

### 2.1 A/B 连接及查询负载矩阵

A 使用实际生产原生绑定，A 开启异步关节推送，A 每 50ms 查一次状态；B 使用实际独立进程观察器。每段约 3 秒，依次建立/查询/注销 B。没有 prepare/arm/Enter/Send/Stop。

| 条件 | A 查询数 | A 平均 ms | A P95 ms | A 最大 ms |
| --- | ---: | ---: | ---: | ---: |
| 只有 A，开始 | 60 | 21.310 | 51.774 | 55.462 |
| B 连接但不查询 | 60 | 21.054 | 49.978 | 63.812 |
| B 按 10Hz 查询 | 60 | 22.827 | 51.093 | 71.760 |
| B 按 5Hz 查询 | 59 | 25.091 | 57.824 | 71.124 |
| B 停查但连接保留 | 60 | 25.107 | 53.972 | 58.563 |
| B 注销，只剩 A | 59 | 26.943 | 56.042 | 76.005 |

B 10Hz/5Hz 分别 31/16 次查询。前后 NIC 的错误、丢弃、碰撞计数均为 0。约 33Hz 的关节回调正常到达，没有反馈过期。这个短时顺序实验不证明 B 完全无影响，但表明 **50ms 慢峰在没有 B 时已经存在**，降低 B 查询频率也没有在本窗口消除它。

## 3. 网口现在查清了什么

车载没有 ethtool 可执行文件。本轮没有安装软件或要求 sudo，通过 Linux `SIOCETHTOOL` 的 **GET** 接口只读取得驱动、链路和驱动统计。

- 驱动 `e1000e`，内核/驱动版本 `6.8.0-138-generic`。
- 实际速度 100Mbps，duplex=half，实际 PHY autoneg=1。
- 本机支持/广告掩码 `0x60ef`；驱动报告链路伙伴广告 `0x4`（旧式掩码中的 100baseT/Half）。这不是独立读到柜端配置页：固定速率对端的并行检测等也可能影响报告，不能直接判定柜端配置为 half 或 full。
- 当前 `tx_abort_late_coll=1`、`tx_window_errors=1`、`tx_errors=1`、collisions=2；RX CRC/frame 等错误为 0，tx_timeout_count=0。迟碰撞值得优先核对双工不匹配及物理链路条件，不能仅靠这些计数确定是哪一端或哪根线。
- NetworkManager 保存的 `auto-negotiate=no,speed=0,duplex=--` 与实际 PHY 开启协商不是一回事；未指定速率/双工的配置不能直接按“当前 PHY 强制关闭协商”解读。
- eno1 路由 `192.168.1.0/24` 未配置 quickack；没有修改链路、路由或 NetworkManager 配置。收尾 `ss` 无柜端连接。

**可执行的物理处理：** 先读取柜端相连端口实际速率、双工、协商设置，确认两端匹配；若柜端固定 full、PC 协商后落为 half，应协调两端设置，而不是只改 PC 猜 full。核实连接路径与插头/线缆，必要时换已知良好的网线。修复以实际生效模式、故障计数增量和业务时序确认，不以“网线已经插着”或“Ping 通”判定通过。当前无法远程读取柜端端口；不擅自单边强制设置导致掉链。

## 4. 复用历史证据，不重跑无区分度运动

- 原遥操 961 次调用全 rc=0，但段内送点只有 27.04Hz；SDK P50 52.077ms、最大 534.858ms。17 次异常停止都是状态接收过期；Grip、VR 输入与 IK 目标当时仍新鲜。主要不是 Wi-Fi 真断线，而是控制会话的保护退出。
- 首点与实测对齐最大约 0.00022°，无需重复重写首点；恒定当前姿态保持也失败，不需要 VR 变化就可复现。
- 16:07 PCAP：一次 cmd77 SDK 总耗时 217.966ms，请求约 +0.063ms 上线，柜端 TCP ACK 于请求后 35.958ms 已确认全部请求字节，匹配业务响应在请求后 217.706ms 才到，之后 SDK 约 0.198ms 返回。约 181.748ms 在 ACK 后至业务响应到达之间。该窗口无有效载荷重传、序号缺口、零窗口或新增网卡错误。因此本次新重传不能覆盖解释历史这个窗口。
- 17:27 独立进程保持 69 次调用 P50 51.501ms、最大 209.521ms，IPC 最大约 0.246ms，仍状态过期。现有调用区间分析：没有与 B 查询在途区间重叠的 36 次 A 调用仍有 60.178ms 长尾；重叠组更慢只是相关性，长调用天然更容易重叠，不能据此证明锁竞争。即使不重叠，也不能排除早先请求的延后作用。
- 真实发送层仍只有每次提交的 0.15 位置 EMA。IK 内部按 5ms 限幅不等于实际跳帧后的发送点满足速度/加速度约束。丢点/等待后继续收新目标会改变真实送点轨迹；仅把 dt 截为 20ms 不能修复空档，也不能保证真实伺服的加速度。

## 5. PE 与接口资料已确认的边界

用户给的在线 SDK ServoJ 文档属于 ARCS；ARCS 安装/迁移页面不是此 PE 接口契约。官方历史 master 驱动存在双连接 + 单点 + 水位控制；Noetic 存在三连接 + vector 批量。因此“只要双连接必定不支持”“必须批量单点不支持”都不是有效结论。

[Issue #89](https://github.com/AuboRobot/aubo_robot/issues/89) 的原文是关闭 IO 发布/降低定时查询后抖动减轻、但仍抖动，不是厂家确认“所有 Get 抢同一把柜端锁”的结论。

SDK 单点 TCP2CAN 先做 FK、封装为一个路点 vector，再走 cmd77 同步业务请求/响应；vector 共享这条传输路径。TCP ACK 只证明对端 TCP 层收齐字节，不代表其业务线程已读请求、入队、下发 CAN 或电机执行。透传绕过哪些规划步骤与“没有控制处理/网络等待”不是同一个命题。

本轮读取的停止状态诊断原值 `buffer_size=1200,buffer_data=0,interrupt=0`。对应字段在此 SDK 标为预留；这不证明点数/字节单位、运行有效性或 1200 个点容量，更不能用它坐实或否定某个 3–4 帧环形缓冲假说。

## 6. 剩余问题、观测限制与具体实现方向

| 项目 | 当前状态 | 还缺的精确信息 / 动作 |
| --- | --- | --- |
| VR/IK、首点是否主因 | 已复用记录；保持也复现 | 只有不同新证据才重开，不重测头显/相机 |
| 状态是否用异步反馈 | 已确认关节为异步，完整 RobotState 为 B 查询 | 不以关节/事件代替未经保证的完整状态 |
| 第二连接是否必要原因 | 单连接开推送即可出现慢峰；分进程仍失败 | 不能承诺删 B 恢复 100Hz；分工还需透传验收 |
| 推送与请求交互 | 已真实 ABABA 复现 | 精确机制缺逐包/柜端分段时序；当前足以支持分工方向 |
| 网络是否绝对健康 | 否；新 TX 错误、迟碰撞、重传已观察 | 柜端相连口配置、物理路径核对和协调修复 |
| ACK 后约 182ms 内部位置 | 外部边界已固定 | 柜端业务收请求/入队/CAN下发/应答准备/实际发送的分段记录 |
| PE 点消费、缓存和停止 | 未取得覆盖本版本的契约 | 单点/vector 消费周期、应答含义、水位单位、欠载/满载、Stop/Leave/断线清理语义 |
| 位置/速度/加速度连续性 | 生产代码缺口已确认 | 按已确认 PE 时序与机型约束实现实际下发层；不能宣称20行等价ARCS servoJoint |
| 实机可用性 | 当前未通过 | 保持 → 有限单关节 → VR，前一级通过后才推进 |

**柜端入口现状：** 由车载连接 192.168.1.5 的 22/5900/80/443 均拒绝连接；没有尝试口令、启用服务或广泛扫描。用户当前不方便查日志导出入口。现有权限无法进入 PE 内部诊断，这是明确的外部观测限制，不是已经定位到 CAN 或证明控制柜硬件坏。

**反馈分工实现应满足：** A 仅持有运动 SDK，不订阅关节流；B 负责异步关节推送和完整状态查询。B 的关节回调发布路径必须与阻塞状态查询解耦，使用独立遥测通道把原接收时间、序号、会话代次送到父进程；不能把角度塞进 `query_state()` 应答后才发布，否则 B 一慢，两种反馈会一起饿死。A 继续检查关节/状态分别 200ms 新鲜度、SDK预算及撤销代次；停止确认依赖停止之后的新反馈。当前 `ProcessStateObserver` 的请求/响应管道只发布状态，直接搬回调不够，需明确增加这条遥测路径。

接收后 QUICKACK 可作为明确目标端点、可关闭的诊断/优化项；它不能修复迟碰撞/重传，也没有保证透传最大等待。当前没有把新分工或 QUICKACK 当作已验收生产修复。先处理已出现的链路错误，再实施并验收这一路径；柜端契约仍缺失时，不用盲目深缓存或取消保护来绕过。

厂家待确认内容已整理在 [具体问题单](aubo_tcp2can_vendor_questions_2026-11-08.md)，未对外发送。已有证据足以定向问版本兼容、ACK 后分段诊断及停止/队列规则，不再要求用户反复进行无目标测试。
