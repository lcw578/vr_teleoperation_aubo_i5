## 2. 总体架构：连接与通信方式

**裁决：单机闭环。遥操迁上车载电脑，相机同机采集，训练数据不跨机。**

```text
两台 L515 ──USB3(已验证)──→ 车载电脑 xc-pc
                              ├─ 相机采集进程（pyrealsense2，双出口：WebRTC 头显画面 / 录制落盘）
                              ├─ 遥操链（自笔记本迁入）：relay:8443 ← Quest
                              ├─ recording.py 25Hz 快照 + 事件流
                              └─ export_lerobot → LeRobot v3.0（25fps）
        ┌──────────────────────┴─────────────────────┐
   有线（静态 IP）                          Wi-Fi 192.168.3.x
        ↓                                        ↓
   控制柜 192.168.1.5              Quest（USB adb reverse 优先 / Wi-Fi 直开 8443 兜底）
                                   笔记本（SSH 启动/监控/取数据）
```

| 链路 | 方式 | 载荷 | 带宽 |
| --- | --- | --- | --- |
| 车载电脑↔控制柜 | 有线直连 | Follow 命令+关节推送（现有链路原样） | <1Mbps |
| Quest↔车载电脑 | USB adb reverse（主）/ Wi-Fi 直开 https://IP:8443（备） | 手柄位姿+录制 HUD | 极小 |
| 笔记本↔车载电脑 | SSH + 状态页 | 启动/监控/数据集回传 | 只搬压缩数据集 |

网络配置（车载电脑，有线口名以 `ip -br link` 实查为准）：

```bash
nmcli con add type ethernet ifname <有线口> con-name robot-cabinet \
  ipv4.method manual ipv4.addresses 192.168.1.100/24 \
  ipv4.never-default yes ipv4.ignore-auto-dns yes ipv6.method ignore
```

照抄笔记本 10-26 调好的配置（静态、清网关、never-default）。⚠️ 迁移后笔记本的
enp3s0 上 192.168.1.100 配置必须停用（`nmcli con down`），防 IP 冲突。

**明确不做**：图像跨机实时传输进数据集；ROS 进入运动链；笔记本参与控制路径。

## 3. 频率定案

| 频率 | 定案值 | 依据 |
| --- | --- | --- |
| IK/控制核心 | 200Hz 期望（现状不变） | 内部，不进数据 |
| 命令提交 | 请求 25Hz，实测 ~22Hz | 【实测】提频无效已证；对 π0.5 部署（chunk 步长 25Hz 量级【外部资料】）已够 |
| 关节反馈 | ~33Hz（柜端推送周期 30ms【SDK PDF p.34】） | 状态源 |
| 数据集帧率 | **25fps**（用户定），导出保持 25 或按需 `--fps 20` | LeRobot 只要求正整数【已核】；π0.5 端 resize 224×224、低 fps 可重采样【外部资料】 |
| 相机 | 30fps RGB；720p 优先（对齐 HarvestFlex【外部资料】），USB 受限时回退 480p | 已验 480p；720p 需复测双流 |

结论：**20Hz 量级控制频率可行，维持现状即可；采数 25fps 达标。采数不被链路优化阻塞。**

**2026-11-01 用户拍板（冻结）**：采数基线 = **串行状态查询 + Follow 25Hz 请求（实测 19-22Hz 聚合）+ 录制 25fps + 相机 30fps**；双连接对照实验不做（+3Hz 收益被导出配对吸收，且串行是唯一有干净实机履历的配置）。重新考虑的两个触发器：①导出侧"状态年龄>200ms 丢弃帧比例"持续升高；②厂家开通 ARCS/RTDE（届时提交率问题整体消失）。

## 4. 链路优化工作项（与采数并行，不阻塞）

### 4.1 全双工排查（用户工作项 ②）

先讲清区别【网络通识】：半双工=一条独木桥，双向不能同时，两头同时发→冲突/坏帧→静默丢帧→
TCP 重传；全双工=两车道，这类丢包机制性消失。带宽不是问题（包很小），丢包才是。

操作顺序：
1. 连机后 `ethtool <有线口>`，看 "Link partner advertised link modes"——**对端通告什么才可能协商出什么**；
2. 先换一根确认好的 Cat5e+ 网线再读一次（劣质线会让协商降级，也是 SACK 丢包的头号嫌疑）；
3. 换线后对端通告含 Full → 自动协商自然出全双工，PC 不改任何东西；
4. 仍只通告 Half → 查柜侧：CB 柜多个网口挨个试、示教器服务菜单查端口模式；
5. ⚠️ 禁止 PC 单方面 `autoneg off` 强制全双工（对端半双工时=双工不匹配，更糟）；
6. 加千兆交换机做隔离对照（顺带提供干净抓包点）。

验收判据（hold/fail）：

| 指标 | 现状 | 过 | 挂 |
| --- | --- | --- | --- |
| Follow 调用 P95 | 58–60ms | <45ms | ≥45ms |
| 推送空档最大值 | 228–261ms | <100ms | ≥100ms |
| 抓包重传/SACK 缺口 | 实锤 1 次 | 30min 会话 0 次 | 再现 |

**§4.1 实测结论（2026-11-01，ethtool 留档）**：PC（r8169）自协商开启、通告
10/100 Half+Full + 1000F；**对端（柜）只通告 `100baseT/Half` 且 `auto-negotiation: No`
——柜端网口为强制 100M 半双工、不参与自协商**，PC 按并行检测规则只能落到 Half。
⇒ 换线不能带来全双工；全双工唯一路径=柜端改配置或换柜上其他网口（柜面板照片 2026-11-01：
可见 Ethernet×1 + USB3×2 + Modbus RTU DB9，其余口待徐灿/厂家确认，不自行开柜）。
换线目的收窄为排除劣质线缆坏帧（SACK 缺口机制）。⇒ 厂家清单加问："柜端网口能否改为
自协商或 100M Full？"。同日补测：ping 192.168.1.5 RTT 0.104ms（mdev 0.006ms，0 丢包）
——纯线路往返 0.1ms，40ms 中位非线路传输所致。

**§4.2 实测结论（2026-11-01，✅ 归因完成）**：基线会话（Follow 25Hz + USB 遥操，3334 次调用
+ 同步抓包 27021 包）判定如下——
1. **线缆/丢包：无罪**。双向 TCP 重传 = 0；ping 0.104ms/0 丢包。10-29 的 SACK 缺口为偶发
   事件，非常态；换线对照分支关闭（无丢包目标可测）。
2. **PC 主机侧：完全无罪**。3334/3334 次调用 0.08ms（中位）/0.19ms（P95）上线，最大 0.77ms；
   候选→SDK 开始 2.45ms。
3. **柜端 8899 服务：主犯**。调用时长双峰：**48% <15ms（min 5.3ms，柜子有快路径）、
   49.6% 40–60ms、15–40ms 死带仅 0.5%**。网线侧 Δwire 同形状（41% <8ms、26.6% 40–60ms）。
   推断（非证实）：柜端服务循环节拍 ~40ms，相位对上立即应答、错相位等下一拍；与吞吐天花板
   1/40ms≈25Hz、J6 低速实验 5.35ms 下限、历史 22–25Hz 收敛全部自洽。慢应答不随 PC ACK
   释放（与前 PC 包间隔中位 6.3ms，快慢两模相同），排除 Nagle×延迟ACK 释放机制。
4. 附带：本轮推送间隔中位 40.4ms（≈25Hz），与文档 30ms/历史实测 31ms 不同——柜端推送节奏
   随状态变化，记录待观察。
5. **修 40ms 只剩厂家一条路**（证据文件：link-before-20261101-095423.pcap +
   follow25-before-20261101-095434.jsonl）。本轮长尾实测良好：>100ms 仅 0.1%。

### 4.2 一次抓包归因中位 40ms（先诊断后开药）——原判据表，已被上方实测结论取代

`sudo tcpdump -i <有线口> host 192.168.1.5 -w follow.pcap`，跑 5 分钟正常遥操：

| 抓包特征 | 判给 | 后续 |
| --- | --- | --- |
| 请求出→响应入 Δwire 中位 ~35–40ms，无重传 | 柜端服务耗时 | 厂家清单（附抓包文件） |
| 响应段发出紧跟 PC 的 ACK（等 ACK 模式） | Nagle×延迟ACK | PC 侧 TCP 选项实验或厂家 |
| 同序列号段出现两次、间隔 ~200ms | 丢包重传 | 回到 §4.1 |

### 4.3 头显 USB 直连 A/B（用户工作项 ③）——✅ 已验证（2026-11-01）


实测结论：USB 显著优于 Wi-Fi。B 轮（USB，只读预览会话）实测：中位帧率 90.2Hz（Quest 满帧）、
全程采样最大接收间隔 15ms、**0 次 >100ms/>200ms 空档**、src_gap==gap（传输零附加抖动）、
活跃操作期 90s 仅 1 次 ~0.5s 波动；seq 冻结的 54s 为操作者摘头显的 XR 暂停，不计传输。
对照基线=10-29 文档 Wi-Fi 实测（输入空档 205–209ms 多次、极端 1005ms）；未跑同日 A 轮，
但差距为数量级，结论成立。采样器：`scripts/aubo_input_timing_sample.sh`（注意：状态页
/aubo/status 只输出 last_received，不含 recent_received——帧率/停顿核算用 seq 缺口法）。

正式用法：插线 → `adb reverse tcp:8443 tcp:8443` → 入口加 `--usb` → 头显开
`http://localhost:8443/`（http 免证书）。adb reverse 在重插线/重启后需重敲。
车载电脑侧同样适用（`apt install adb`）。WebRTC 视频为 UDP 不走 adb reverse，
将来"USB 位姿 + Wi-Fi 视频"两腿并行。

```bash
sudo apt install adb
adb devices                     # 头显弹"允许 USB 调试"→ 允许
adb reverse tcp:8443 tcp:8443   # 头显浏览器开 https://localhost:8443/
```

注意：头显代理必须关（防 localhost 流量绕回 Wi-Fi）；换 URL 后腕部校准重做一次；
迁车载电脑后同样适用（装 adb 即可），线长 5m 内（采数时车是停的，够用）。
A/B 测法：同一 5 分钟会话协议各跑一轮 Wi-Fi/USB，对比 `--diagnostic-output` 里
input_age 均值/P95 与输入空档次数（预期：USB 传输层 <2ms、空档 0【估计】）。
已知限制：WebRTC 视频是 UDP，adb reverse（TCP）带不动——将来"位姿走 USB+头显看相机画面"
需两腿并行（视频走 Wi-Fi ICE 直连）。

## 6. 录制与数据集方案

- **进程结构**：遥操+recording.py（现状原样）+ 相机采集进程（独立，不碰控制循环——
  `aubo_hardware_deployment_plan` 阶段 5 硬约束）。相机进程双出口：
  ① 最新帧槽→aiortc WebRTC→头显（复用 vr-teleop-kit 管道，底层由 cv2/V4L2 换
  pyrealsense2——L515 非 UVC 设备，fork 已留 camera registry 接口【代码证据】）；
  ② 有界队列→MJPEG+时间戳落盘（展示用 latest-slot、录制用 bounded queue，二者必须分开）。
- **时间戳**：主=主机 monotonic（双流实测无抖动）；辅=设备帧号+hardware_clock
  （设备钟慢 ~0.4%，禁作对齐基准）；可选验证 RS2_OPTION_GLOBAL_TIME_ENABLED。
- **导出**：`export_lerobot.py` 扩展图像配对（每帧配之前最近状态，年龄超限丢弃并标记），
  LeRobot v3.0、25fps。三路相机 key：scene_left/scene_right → base 槽位，D405→wrist 槽位（后续）。
- **后续增量**：夹剪一体夹爪=状态/动作各加 1 维（RS-485 驱动复用 `gripper_driver_v2` 先例，
  注意其 disconnect 禁扭矩行为）；D405 上腕后加第三路。

### 6.1 相机链路验收结论（2026-11-01，✅ 三步全过，720p 定档）

- **时间戳验证 PASS**：双机 30.03fps/0 缺口/主机间隔 max 33.6ms；设备钟漂移实测 **4035-4039ppm**；
  **hardware_clock+每会话线性拟合残差 std 0.05ms/max 0.25ms——优于 SDK global_time 映射（std 4.1ms）**。
  定案：主时间戳=主机接收；辅助列存原始 hardware_clock（**不开 global_time**）；需设备侧交叉审计时
  按会话线性拟合。
- **480p 双流 PASS**（30.02fps/0 缺口/回放一致/峰值 RSS 109MB）。
- **720p 双流 PASS（定档）**：首跑右机 1 帧缺口（1754 帧丢 1），复跑 **0 缺口** → 偶发，非系统性。

- **USB 拓扑（lsusb -t）**：两台 L515 直插同一条 **10Gbps 根控制器（Bus 02）** 的 Port 3/5，

- 工具：`scripts/camera_timestamp_check.py`、`scripts/camera_record_short.py`（独立单文件，
  已在车载电脑实跑；教训：脚本须在开跑前核对在线设备列表——当日右相机曾掉线导致白跑）。

## 7. Placement 一键放置（用户工作项 ⑤，设计稿）

### 徐灿现状【代码证据：/data/robot_ws_dev/src/xc_aubo_arm_control/】

- **不是 MoveIt**：ROS 2 服务节点包 AUBO SDK 2.5.0（`motion_service.cpp` + `libaubo_sdk.so.2.5.0`，
  与我们同代 SDK），运动 = **固定过渡点结构**：初始位置 →(关节运动)→ 过渡点 →(直线运动)→ 采摘点；
  返回 = 采摘点 →(直线)→ 过渡点 →(关节)→ 初始位置。
- **"采摘后返回果箱服务"已存在**（`说明.txt` 30004/30005 错误码），即放置动作的服务化版本已在他处部署。
- 每段有独立碰撞检查（`auboi5_path_check.cpp`，错误码 31001–31004）与逆解检查（30001–30007）。

### 集成路线对比

| 路线 | 说明 | 评估 |
| --- | --- | --- |
| A. 复刻进遥操链【建议】 | 在 teleop/aubo 内加 placement 模式：按徐灿的过渡点结构（提升→平移至收集框上方→到位），复用左 Y 回位的既有机构（示教位姿 JSON + 主机路点生成 + follow 流发送 + 20°/s 等参数约束 + 反馈监控/撤销） | 单一控制程序、复用全部安全机制与录制事件流；工作量大头是多点序列与直线段（左 Y 目前是关节空间直插） |
| B. 调用徐灿服务 | 遥操进程 → ROS 2 服务 → 他的节点（自己的 SDK 连接）发运动 | 引入 ROS、两个进程同时连柜（多客户端控制权语义未核实）、控制权交接复杂 |
| C. 柜内 MoveJoint 逐段阻塞 | SDK 点到点接口直接走三段 | 实现最简，但绕开遥操链的监控/撤销/录制语义，与既有安全架构不一致 |

裁决：**A 为主**，B/C 作为与徐灿核对后的备选。A 的关键待办：确认徐灿的过渡点选取原则
（提升高度、平移路径是否避植株）、直线运动用的 SDK 函数与参数、释放时序，然后
把"返回果箱"三段映射为 placement 序列。

### 按键与门控【建议】

- 按键：**右 B**（`aubo_quest_follow.md` 明示未分配）；网页按钮作后备。
- 前置门控：夹爪确认闭合（当前实体未接夹爪=人工确认；接夹爪后=RS-485 状态位）+
  无故障锁存 + 有效反馈 + 遥操处于接合或待接合状态。
- 流程：按 B → 遥操撤销发送许可（复用 Grip 释放路径）→ placement 序列执行（每段同样受
  范围/时效/监控约束）→ 到位 → 释放夹爪 → 事件标记 placement_done → 操作者 Grip 重新接合。
- 录制语义：placement 段的目标照常进 action 流（SDK 已接受目标），起止打
  `placement_start/done` 事件——将来策略若要学放置，示范已在数据里；若永久脚本化，
  导出时可按事件掩掉，两不误。
