# 双连接第四轮：新反馈被误判为未来数据的时间顺序修正

## 现场根因与边界

本轮依据用户要求，先完成现场与离线定位，再修改。现场完整诊断为 `/data/VR_teleoperation_runtime/follow50-idle-gap-20261028-203617.jsonl`；详细分析保留于同目录 `aubo-fourth-root-cause-20261028.md`、`aubo-fourth-cause-analysis-20261028.json`。

在两次正常 Grip 释放和重新接合后，第三段运动发生永久锁定。故障前45次Follow调用全部成功，307次B状态查询全部成功。故障消息中关节反馈仅13微秒、状态反馈16.624毫秒，却被原生标为 `observation_pending`。随后Python按运动阶段异常撤销许可、慢停并确认停稳，但fatal锁保留。现场没有证据表明这是实际200毫秒过期或SDK调用失败。

原生 `refresh_parallel_observation()` 先取检查时间，再锁定并读取最新关节推送。回调若恰好在两步之间发布，新样本时间合法地晚于旧检查时刻，触发“未来数据”拒绝。该函数由snapshot、arm及send_joints共同使用。同类隐患也存在于watchdog：先取时间、后读B状态结果，刚发布的健康结果可能因负年龄而被锁定。后者已离线复现，但不是本轮现场首因。

上一轮空闲过期修正保留，详见[空闲反馈排查](aubo_parallel_idle_feedback_2026-10-28.md)。本次修正针对更底层的时间顺序竞争，不能用空闲恢复规则或扩大阈值替代。

## 修改

`teleop/aubo/native/follow.cpp`：先复制B状态、关节推送及各自接收时间，再读取同一检查时刻验证两份副本。原始时间戳不改变，检查仍要求年龄非负且不超过200毫秒，关节有限、状态有效。snapshot、arm和send_joints自动使用同一修正。

`teleop/aubo/follow.py`：watchdog先读取要检查的运动线程记录和B状态副本，再读取检查时间，消除成功B查询在读取期间发布造成的负年龄误判。SDK调用预算、真实状态过期、停止期限及故障锁定政策保持。

没有取绝对年龄、将负数钳成0或忽略ObservationPending。没有新增设备查询、登录、重连、参数写入，也没有改变50Hz请求节拍、Grip规则或作者IK。

## 确定性复现与回归

新增测试先在修正前运行，以下4项全部按预期失败，再用相同时序验证修正后通过：

1. 在关节缓存读取边界发布回调，snapshot必须返回新鲜观测。
2. 在同一边界发布回调，arm不能误拒绝合法接合。
3. 在同一边界发布回调，send_joints必须使用新测量并正常提交。
4. 在watchdog时钟/状态读取边界发布一次成功B查询，不能误杀查询线程或锁定运动。

另加两项保护回归，分别注入真正过期和未来时间戳：原生快照保持不可用、arm及send仍拒绝；watchdog仍报告state_reception_expired并要求停止。原有离线用例覆盖运动反馈过期、实际SDK超时、迟到结果失效、Grip恢复、多轮空闲推送中断、停止确认期限及透传/J6隔离。

交错及时间戳注入钩子仅在假SDK绑定编译时启用。正式目标直接编译生产follow.cpp且未定义测试宏，正式模块没有注入入口。假SDK测试通过对应实例的回调缓冲区发布，暂停周期推送会等待在途周期回调结束，避免不同测试实例或背景推送干扰指定交错。

最终正式绑定与假SDK绑定均已构建，正式模块哈希与follow-build.json一致。完整离线检查通过295项：274项Python单元、21项生产绑定/假SDK集成；另有正式绑定未连接拒绝、原生profile/透传生命周期、默认入口及Shell检查。
