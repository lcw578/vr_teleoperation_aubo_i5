# 2026-11-08 TCP2CAN 实机抖动与控制中断排查

结论：本次接入版本尚不适合继续作为实机遥操基线。完整 VR 会话的送点能力明显低于最小测试，存在不均匀位置指令和 200–535ms 阻塞；按住 Grip 时的中断已定位为运行状态反馈过期触发主机保护。机械异响的唯一物理根因尚未确认。

本轮只读检查运行中 HTTP 状态、已有录制文件、源码及网卡状态；没有发送运动指令、运行新运动测试、重启程序、变更网络或放宽保护阈值。

## 1. 原始证据

- 车载进程 PID 46599，入口 `--command-mode passthrough --parallel-state-query --waypoint-feedback --gripper --record`。
- 录制源：`/home/xc/code/lcw/VR_teleoperation_runtime/recordings/aubo/20261108-142113-351517c8/streams.jsonl`。
- 原始数据与分析脚本实际存储于 `/data/VR_teleoperation_runtime/passthrough-incident-20261108/`：`streams.jsonl`、`live-status.json`、`analyze.py`、`analysis.json`。
- 截取数据包含 9046 行，其中 7097 条 XR、1922 条 SDK attempt/returned 事件（961 次完整发送）、20 次硬件事件、7 条夹爪事件。
- 未启动 episode；但会话级 SDK 与硬件事件仍有记录，因此可复核整个送点过程。

## 2. 完整遥操不是 100Hz

| 指标 | 本轮实机记录 |
| --- | ---: |
| SDK 返回码为0 | 961 / 961；不代表运动平顺或已到位 |
| 接合段 | 20 |
| 同一接合内相邻发送起点间隔样本 | 941 |
| 段内加权发送频率 | 27.040Hz |
| 发送起点间隔 P50 / P95 / 最大 | 52.265 / 61.995 / 171.872ms |
| SDK 耗时平均 / P50 | 40.247 / 52.077ms |
| SDK 耗时 P95 / P99 / 最大 | 64.278 / 214.193 / 534.858ms |
| 相邻发送间隔 >40ms | 566 / 941（60.15%） |
| SDK 调用 >=200ms | 13 / 961 |

27.040Hz 计算为 `941 / sum(941个段内起点间隔)`，剔除接合段之间的停顿。最后一条长调用之后没有下一条段内发送，故不进入起点间隔；不能将其当作对所有停顿的完整指标。SDK 耗时分布包含这些末次长调用。

调用耗时有明显双峰：359 次 <10ms，557 次在 40–80ms。请求周期 5ms 只是上位机的最短请求间隔，同步 SDK 不返回便无法继续送点；多开运动线程并不能安全解决这一点。

## 3. 按住 Grip 的“断连”有确定触发原因

20 条硬件事件中，3 条为正常 `grip_released`，17 条为 `state_reception_expired`。

对 17 次状态过期逐条匹配最近 XR，右 Grip 全为 true。触发时记录的输入年龄最大 10.888ms，IK 目标年龄最大 5.153ms，均远未到输入 1s / 目标 100ms 的过期阈值。触发原因是 B 连接运行状态缓存过了 200ms，而不是这 17 次 VR 先失联。

最后一次时间线，单位为主机 monotonic 秒：

| 时刻 | 事件 |
| --- | --- |
| 12453.104467 | 最近有效 B 运行状态返回 |
| 12453.155694 | A 透传发送开始 |
| 12453.156708 | B 新状态查询开始 |
| 12453.312537 | 状态年龄约208.07ms，触发撤销；VR输入年龄4.72ms，目标年龄3.78ms |
| 12453.658153 | B 查询超过500ms预算，锁定 `state_observer: query_over_budget` |
| 12453.684037 | B 返回，实际耗时527.329ms；已经失效的结果不重新授权 |
| 12453.690551 | A 返回，耗时534.858ms，rc=0，`revoked_during_call=true` |
| 12453.690614–12453.744651 | 退出透传返回0 |
| 12453.744651–12453.785495 | slow-stop返回0 |

读取时两个机器人 TCP socket 都仍是 ESTABLISHED，Quest WebSocket状态为已连接。这次“断连”主要是控制许可被撤销和故障锁定，不能等同于 TCP socket 断开。

停止确认最终失败：B 观测被预算超时永久置为无效，无法提供停止完成后的新状态；错误内容包括 `valid=0, state_age_s=0.681333, joint_age_s=0.000109`。不能把 `stop_unknown` 解释成机械臂一定未停，也不能仅凭停止 ACK 宣称已经停稳。需操作者从示教器和实体状态确认。

## 4. 抖动相关实现缺口

首帧保持已经核实：20 次接合都发送了 first_measured_hold，与发送前最新反馈的最大差约0.000219°。这不支持“本轮首帧大幅跳变”作为主要解释。反馈也不是编码器同时刻的无延迟样本。

相邻实际下发目标的最大单轴变化：P50 0.129835°、P95 0.405562°、最大0.881717°。这是命令点变化，不能据此推断机械臂真实速度、加速度或柜端执行周期。

`follow.py` 只有 `previous + 0.15*(latest_ik - previous)`。原生 `send_joints` 检查许可、时效、范围，没有相邻透传点速度/加速度/jerk约束。上游 IK 5ms单步限幅也不能保证下游跳过中间候选后仍连续。

发送起点约5ms与约53ms交替，位置滤波每次调用固定推进15%，没有随时间定义的运动状态。同样大小的位置变化在不同时长下代表不同命令斜率；位置EMA不能补齐SDK阻塞期间没有送出的轨迹点，也不能保证反向或停止时加速度连续。

固定系数还增加滞后：对固定阶跃目标，残差为 `0.85^n`，到90%约需14.17次更新。若更新间隔52.265ms，仅滤波模型便约0.740s（按完整帧计15次约0.784s）。这是模型估算，不是本轮端到端延迟测量。

因此“不规则稀疏送点+发送层缺少连续轨迹约束”是有代码和命令数据支持的抖动机制。无高频执行端测量和声音同步记录，无法把异响唯一归因为此；柜端缺点/缓存行为、SDK竞争和网络等待仍需区分。

## 5. 实际有线链路异常线索

只读查询得到 `eno1: speed=100, duplex=half, operstate=up`，累计 `collisions=57, tx_errors=18`，RX errors/drops为0。之前最小测试报告记录累计TX errors=17；本轮没有运动前同窗口基线，不能把新增1次准确归属于本次VR。

NetworkManager配置字段为speed=0、duplex未设、auto-negotiate=no；这些配置字段不足以还原PHY与对端实际协商，当前内核报告的100Mbps半双工应优先核对。碰撞计数与半双工使物理链路/两端双工配置成为优先排查项，但尚未证明双工不匹配或本次每一次长尾均由它造成。

`ss -ti` 还显示A连接累计重传1次、480字节。它支持本连接发生过重传，不足以单独归因17次停止；没有本轮抓包，不能认定Nagle、Delayed ACK或环形缓冲深度。

## 6. 修复顺序与边界

1. 暂停当前透传入口的实机接合；当前进程已故障锁定，不自动重启、清锁或重接合。先确认实体停稳。
2. 优先核对电脑与控制柜两端网口协商、双工配置和网线。不能猜测后单边强制全双工，也不能只改QUICKACK声称已修好。当前机器没有ethtool可执行文件，本轮未安装工具或变更网络。
3. 实机并行SDK连接没有达到离线假SDK的无干扰表现。A/B同时慢并不能确定是共同网络、柜端服务还是SDK内部竞争；先修复链路，再确认支持的多连接/状态推送方式。不能把状态查询重新塞进发送循环，也不能无反馈裸跑。
4. 在透传执行层增加明确的关节速度/加速度连续轨迹生成、发送中断后的停车与重锚定规则。EMA可作为输入降噪的一部分，不能替代这些约束。柜端单点消费周期、欠载与退出语义需核实后才能决定是否需要短批量缓冲。
5. 保留反馈过期和SDK预算保护。不要将200ms/500ms阈值简单放大来掩盖不稳定。观测通道故障后的只读停止确认恢复可以独立改进，但不能恢复运动许可。
6. 当前只做分析与证据保存，不发起新的运动测试。后续任何实机验收应在上述问题修复后进行；已有502项离线回归通过仅证明软件分支行为，不能作为实机连续供点或平顺性的证明。
