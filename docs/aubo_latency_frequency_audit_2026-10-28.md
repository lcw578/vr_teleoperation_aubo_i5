# 当前六轴 Follow 链路耗时与最大发送频率审查

审查日期：2026-10-28。正式基线：`--execute-six-axis --command-mode follow --waypoint-feedback --rotation world --duration 1800`。用户已现场确认 Grip 两次按压问题解决，本轮不再修改该恢复规则。

本轮读取当前源码、既有实机日志、运行进程的本地 `/aubo/status` 和操作系统 TCP 状态；没有新建 SDK 连接，没有重启当前会话，没有发送运动、停止、参数或模式切换指令，没有修改控制代码。

## 结论与证据强度

1. **当前程序对 Follow 的发送节拍上限为 20 Hz，不代表实际稳定达到 20 Hz。** Python 在上次 SDK 开始发送后不足 50 ms 时不发送；查询和发送超时会拉长间隔，不补发。原生六轴发送没有独立的 50 ms 最小间隔检查；Python/native 的 profile 一致性检查仍需在未来修改节拍时保持一致。
2. **尚不能给出这台机械臂、当前 SDK/固件和整条链路的最大稳定频率。** 现有证据不支持稳定 200 Hz；也没有完成 25/40/50/100 Hz 等逐级对照。不能把 20 Hz 误称为厂家接口上限。
3. **优先瓶颈是同步 SDK 请求及与发送串行的状态查询，且存在明显长尾。** 最新候选到 SDK 开始的历史均值约 2 ms，但发送调用可达几十至数百毫秒。Python/native 分开线程并释放 GIL，不代表 SDK 本身异步。
4. **反馈实际约 33 Hz，与 200 Hz IK、20 Hz 发命令是三个不同频率。** 推送是接收时间戳，没有柜端采样时钟。历史回调间隔最大超过 200 ms，反馈保护和观测延迟仍需审查。
5. **尚未测到真正的“手部动作到机械臂动作”端到端延迟。** 现在的 candidate 时间戳不能替代原始 XR 时间，更不能替代机械臂开始执行时刻。机械动态响应、SDK 目标覆盖/排队语义仍是独立问题。

## 1. 当前链路与节拍

```text
Quest WebXR requestAnimationFrame
    → 浏览器 JSON / WebSocket / Wi-Fi
    → PC Relay 广播 → 本机 WebSocket receiver
    → 最新 XR 槽 + 保留释放事件
    → 期望 200 Hz：反馈刷新 → 作者滤波/映射/IK → 最新 Candidate
    → 独立 SDK worker：期望 20 Hz Follow 请求
                         ↕ 同线程同步状态查询（active 100 ms 节拍）
    → 原生 io_ 互斥锁 → SDK 同步请求/响应 → 控制柜 → 物理运动

控制柜 waypoint callback → 原生有限缓存 → Python 控制循环/显示
```

- WebXR 每个 XR 帧发送一次，实际帧率由设备/浏览器决定，当前没有逐帧记录证明它是 72、90、120 或 200 Hz。不能用 `core_frequency_hz=200` 推断手柄新位姿率。
- 控制循环期望 5 ms，过期时点跳过。它会对尚未超时的缓存输入继续求解；200 个 candidate 不等于 200 个独立手部观测。
- Follow 50 ms 节拍在 `teleop/aubo/follow.py` 的常量与 `_cycle()` 中执行。上层只保留最新目标，没有上位机运动点 FIFO；这不能证明柜端没有队列。
- active 状态查询按上次结果接收时间加 100 ms 调度，不是严格每秒固定 10 次。查询本身的耗时和其它工作会降低其实际频率。
- 机器人流量实际走 `enp3s0`，`192.168.1.100 → 192.168.1.5:8899`。Quest 的无线链路与机器人有线链路应分别测量。

### 历史 200 Hz 透传试验

来源：`aubo-passthrough-200hz-20261028-152650.jsonl`。期望 200 Hz，40 次发送、13 个短接合段，27 个段内间隔，实际合并约 **10.376 Hz**；调用均值 **77.876 ms**、P95 **175.423 ms**、最大 **222.686 ms**，最小也为 **6.418 ms**。后续不完整转移日志出现过 **289.255 ms** 调用。

该完整试验包含旧的循环累计落后误停，样本少且接合短，不能据此评定透传的最终能力或物理效果；但足以否定“配置 5 ms 就已实现 200 Hz”。不能用它直接替 Follow 定上限。

### 当前运行会话的只读快照

存档：`/data/VR_teleoperation_runtime/aubo-latency-audit-live-20261028.json`。

- 当前进程参数与正式基线一致，`requested_frequency_hz=20`，`diagnostics_enabled=false`，累计提交 1155 次。
- 读取时已松开、SDK worker 为 idle、`fatal=false`、`stop_confirmed=true`；输入已不新鲜。状态保留 `hardware_feedback_unavailable`，首个停止原因是 `grip_released`，不可只凭这个快照重建故障顺序或断言正在故障停机。
- 已完成约 60245 次控制循环，错过周期 0、真实 stall 0。全会话最大 `runtime_step_s` **0.854 ms**、反馈刷新 **0.692 ms**、显示 **3.792 ms**、循环工作 **4.263 ms**。这些是最大值，非分位数；`runtime_step_s` 含协调和核心，非纯 IK。
- 后续两次状态间约 128.77 秒计划时间，增加 25754 次循环、0 次跳过，callback 序号增加 4293，接收率约 **33.34 Hz**。这段处于 idle，不能据此评定运动中负载。

## 3. 审查发现，按优先级排序

### 高：发送前的状态查询直接推迟到期目标与停止请求

位置：`teleop/aubo/follow.py:425–444, 499–505`，`teleop/aubo/native/follow.cpp:100–119, 224–240`。

`_cycle()` 在判断发送是否到期之前，先判断并执行状态查询。SDK send、snapshot 共用一个 owner 和原生 `io_` 锁。即使在等发送期限时提前开始查询，查询超时跨过期限仍会阻塞发送；Grip 撤销只改变本地许可，无法中断已开始的 SDK 调用，停止也要等其返回。

先记录“发送到期但被查询占用”的时间，再考虑发送优先和查询时隙调度。仅把查询挪到发送后无法解决任意长查询跨越下一期限的问题。不要未经 SDK 并发语义核实就把同一实例查询移到另一线程。

### 高：只有新 candidate 年龄，缺少原始输入到发送的关联

位置：`teleop/aubo/shadow.py` 的 `_tick()`、`teleop/aubo/offline_session.py` 的 `Candidate`，`teleop/aubo/analyze_follow.py`。

candidate 每次求解以当前主机时间生成，未携带 XR epoch/seq、接收时刻和浏览器来源时间。一个 2 ms 的 candidate 可能来自更早的缓存 XR 帧。因此“candidate→send 约 2 ms”不能被说成总链路延迟约 2 ms。现有控制循环诊断每秒一条 last/maximum，也无法还原每次 IK/调度耗时分布。

下一步应关联 `XR seq → 接收 → core 消费 → candidate → SDK 开始/返回`；另记录发送间隔和查询阻塞区间。浏览器与 PC 不共时钟，先报告 PC 接收到 SDK 的同钟延迟，浏览器部分用往返校准/相对排队年龄单列误差，不能直接相减两端时钟。

### 高：不能用更高目标发送率替代物理跟随延迟测量

SDK 确认不等待目标到位，但仍同步等待请求响应。柜端何时采用目标、覆盖/排队方式和控制周期未获得充分证据。当前读取到的 SDK 客户端 profile 不等于柜端速度/加速度配置。

验收应同时比较实际发送间隔、目标/反馈时序、往复动作相位差和目标领先。callback 约 30 ms 一次会限制物理延迟估计的时间分辨率，还叠加未知传输年龄。不能把同一时刻的目标减反馈角差直接除成延迟，也不能先将两条曲线对齐再把误差变小作为性能改善。

### 中：推送常规读取重复转换整个历史缓存

位置：`teleop/aubo/native/follow.cpp:88–98`，`teleop/aubo/follow.py:193–220`。

每个 200 Hz 控制循环复制最多 256 个 Push，再全部转换为 Python dict/list，即使最后只用最新点、没有新序号也仍发生。这是明确的可减少开销；最新会话最大反馈阶段不到 0.7 ms，当前证据下它是次级优化，不是 SDK 数十毫秒长尾的解释。

可让常规读取只返回最新点，诊断读取使用 `since_sequence` 增量接口；保留真实接收时刻、回调历史和序号缺口统计，不减少诊断可见性。

### 中：状态与显示仍与核心共用循环；Relay 会等所有接收端

位置：`teleop/aubo/quest_preview.py:310–379`；`relay/server.py:262–282`。

控制循环每次生成状态，30 Hz 做显示；`PreviewStatus.update` 的递归转换在已计时工作段之后，会算到下一轮间隔，优化时需防止漏算。当前显示最大 3.792 ms，曾经其它会话更慢；可先降低状态生成频率，再比较 headless 与显示开启的分布。

Relay 对全部接收者 `await gather`，单个慢 peer 的发送上限 50 ms，后续关闭还可能增加等待。这不是每帧固定 50 ms，但慢监看端可能延迟同一来源下一帧的处理。应有每 peer 最新值出口和不阻塞输入的广播机制，并保留释放/故障事件语义；目前没有测量证明它是本次主要瓶颈。

### 中：反馈接收长尾和 SDK/native 缓存是两类问题

callback 平均 30 ms，不代表始终连续。完整历史中接收间隔最大 228–245 ms，期间序号连续，说明观察到的是主机 callback 长间隔，不是分析器漏掉保留区间内序号；仍不能仅靠这个判断是设备采样、网络、SDK 接收线程还是主机调度停顿。

此外，显示线程读取到新 push 不会自动更新 native 发送检查的状态/关节快照。现有修正已对过期原生缓存触发刷新。未来优化应区分“新 push 已到但缓存没刷新”和“push 本身没按时到”，不能通过放宽时间戳或 200 ms 阈值解决。

## 4. 最大发送频率应怎样解释

| 问题 | 当前结论 |
| --- | --- |
| 不改当前正式配置，最多请求多少？ | 20 Hz，50 ms；实际会更低 |
| 20 Hz 是厂家接口上限吗？ | 不是，当前项目调度值 |
| 原生六轴调用本身禁止高于 20 Hz 吗？ | 没有独立最小周期拦截；但需维护 profile 校验与有效期约束 |
| 作者核心能否 200 Hz？ | 当前会话在所记录负载下达到了约 200 Hz；不等于 SDK/机械臂 200 Hz |
| 这条 SDK 路径已经证明可稳定 200 Hz 吗？ | 没有，5 ms 周期甚至小于所引完整历史中的最短发送调用 |
| 能否据此认定最大就是 13 或 33 Hz？ | 不能；13.34 是旧版本一场试验的结果，33 是反馈接收率 |
| 最大稳定频率是多少？ | 尚未测得，需要消除长尾/明确设备输入约束后逐级验证 |

单 owner 资源的必要条件可粗略写为：

`f_send × E[T_send] + f_query × E[T_query] + 其它占用 < 1`。

这只是容量约束，不保证周期稳定。例如假设发送均值 20 ms、查询每秒 10 次且均值 20 ms，发送可用时间约 80%，理想平均容量约 40 次/秒，尚未计调度开销；这不是本机 40 Hz 验收值，也不能由这两个历史均值直接替当前版本定参数。P95、P99、最大阻塞和查询冲突决定抖动：50 Hz 只有 20 ms、100 Hz 只有 10 ms、200 Hz 只有 5 ms，一个 60 ms SDK 调用会跨过多个周期。

官方示例“调用后 sleep 5 ms”周期是 `调用耗时 + 5 ms`，也不是严格 200 Hz。500 ms SDK 预算、650 ms 发送间断预算和 2 s 停止预算都是异常检测参数，不是正常性能或额定能力。

## 5. 建议的下一轮实施与验证顺序

1. **先补观测，不先提速。** 运行默认仍为 20 Hz；增加不改变控制行为的轻量聚合窗口：实际 active 发送 Hz、P50/P95/P99/最大间隔、超过 50/100/200 ms 数量、SDK 与查询分布、查询占用发送期限时间、输入→candidate→send 同钟关联、callback 间隔。idle/释放时间不进入发送频率分母。聚合数据应默认可读，完整逐点记录仍显式开启且实际存于 `/data`。
2. **同一正式模式重新采短诊断。** 现有 `--diagnostic-output` 可以先覆盖每次发送/查询/反馈和循环摘要，但缺上述 XR 关联。保持 Follow、world、profile 和动作范围一致，60 秒里做几段连续缓慢往复及正常离合；至少留一段足够长的连续接合。检查 `dropped_events=0`，否则增量/流式保存或缩短试验。当前 1800 秒运行没开完整诊断，不能事后补回所有调用。
3. **优先定位 40–60 ms 与 100–200 ms 调用长尾。** 用 SDK 前后时间、线程调度和有线 TCP 报文对齐，区分请求何时真正发出、响应何时到达、线程何时恢复。抓包限机器人地址/端口和必要报头，不记录 Quest 图像或无关流量。确认后再决定是网络/SDK 配置、状态查询调度还是更换厂家支持的低延迟接口；目前不凭 `ato=40` 直接修改连接。
4. **做最小调度/缓存优化后仍在 20 Hz 对照。** 优先减少不必要历史 push 转换和状态生成，再评估查询与发送期限关系。成功标准是实际间隔更接近 50 ms、长尾和故障减少、目标到反馈滞后没有变差，而非只看发包总数增长。
5. **最后逐级验证频率。** 在确认厂家允许的输入范围后，候选阶梯可用 20→25→40→50 Hz；100/200 Hz 需先证明单次调用及查询策略具备相应预算。每级报告同样的分布、丢周期比例、故障、目标反馈响应与手感，改一个变量。正式频率取满足预先约定延迟/抖动与物理响应要求的最高档，并在选择后做更长会话验证。当前无公开 `--send-hz` 入口，未来参数化需同步 Python/native profile 校验，不能只改一处常量。

可先使用现有短诊断入口（会开启真机运动，留待操作者的下一次现场试验；本审查没有运行）：

```bash
bash scripts/aubo_quest_follow.sh \
  --execute-six-axis --command-mode follow --waypoint-feedback \
  --host 192.168.1.5 --port 8899 --user aubo \
  --rotation world --duration 60 \
  --diagnostic-output "/data/VR_teleoperation_runtime/aubo-latency-follow20-$(date +%Y%m%d-%H%M%S).jsonl"
```
