# 停止 10007：原因、修复和验收

## 结论

本次两次停止失败的直接原因已经通过抓包、SDK 反汇编和真实 SDK 本地复现相互验证：Linux x64 SDK 2.5.0 的停止封装存在锁等待顺序问题。**停止完成事件（44）先于停止请求回执（命令 89）到达时，唯一接收线程被停止调用持有的锁堵住，不能继续解析后面的回执，最终停止调用等满 5 秒返回 10007。**

这里的 10007 是客户端“等待请求响应超时”。不能据此认定机械臂未停止，也不能在没有实测状态时认定已经停稳。本结论针对已取得证据的两次停止，不代表所有接口的 10007 都来自这个问题。

它与左摇杆后是否立即按右 Grip 没有直接关系：第二段开始前，归位末尾的停止调用就已超时，程序进入故障状态，后续 Grip 不能恢复控制。

## 抓包证据

检查了三段已有抓包中的 49 次停止：47 次返回 0，首次回执先于首次停止完成事件或两者同批到达；2 次返回 10007，停止完成事件明确先到。

| 失败会话 | 完成事件先到 | 成功回执到达 | SDK 返回 |
| --- | ---: | ---: | ---: |
| home-field-20261102-142813-h6u3YJ | 22.104 ms | 144.760 ms | 10007，5000.221 ms |
| home-field-20261102-150756-aLHtQW | 10.105 ms | 210.689 ms | 10007，5000.214 ms |

两次回执内容相同：`ProtoRobotMoveFuncResult` 的结果字段为 1（请求有效，需要等待完成），嵌套错误码为 0，文本为 `Success.`。后续还有第二次停止完成事件及控制柜进入停止状态的事件。回执实际已到达主机，并非网络上没有回复。

时间是抓包主机接收时间相对于 SDK 调用开始时间，使用最近的 clock_sync 映射；不是柜内执行时间。

证据位于 `/data/VR_teleoperation_runtime/stop-rootcause-20261102/frames.json`；原始抓包位于 `home-audit-20261102/field/` 和 `home-audit-20261102/restart-review/`。仅导出停止和事件报文，没有导出登录报文。

## SDK 内部因果链

使用的库 SHA-256：`a04ad0aa05b2d46fea5a863fe30698950e6434afeafd5a3eaf605c3f0df0ff1b`。

1. `robotMoveControlService` 为命令 0x59 选择 `this+0x13a78` 的停止完成互斥锁；在 `0x24ac63` 加锁。
2. 它在持锁状态下，于 `0x24ac78` 进入请求响应等待。该等待释放的是响应槽自己的锁，并不释放停止完成锁。
3. 唯一接收线程按 TCP 流顺序处理报文。事件 44 经 `responseProcess` → `realTimeRobotEventResponseService` → `robotRealTimeEventProcess`，在 `0x24f112` 要获取同一把停止完成锁。
4. 如果事件 44 在命令 89 回执之前，接收线程卡在此处，不能继续处理回执、路点推送等后续报文。
5. 发送线程 5 秒后在 `sendRequestWaitResponse` 返回 10007，释放完成锁；接收线程才继续。故障期间路点回调停顿、超时后恢复，与此一致。

这是一种由报文到达顺序触发的暂时互相等待；5 秒超时打破它。单纯增加等待时间不能修正锁顺序。

## 修复

`teleop/aubo/native/stop_compat.cpp` 保留当前 SDK 的同一连接、同一 20 字节 SlowStop（89）请求、原有请求响应处理和原厂响应解析器，但绕过 `robotMoveControlService` 的完成锁等待封装。

新的停止流程：撤销后续运动目标 → 发出缓停请求并确认回执有效 → 由 Python 现有逻辑检查请求返回之后的新鲜状态和关节反馈 → 只有状态为停止且关节连续静止才允许完成归位或重新接管。

因此 native 返回 0 的语义是“缓停请求得到成功回执”。物理停止确认仍由 `J6FollowWorker._stop_and_confirm` 执行：新鲜 RobotStopped、关节变化不超过 0.02° 且持续至少 0.1 秒。2 秒调用 watchdog 和 2 秒反馈确认预算保留；真实超时、响应错误、反馈失效、仍在运动均保留故障处理。

适配器通过配套头文件取得 SDK 的基础服务成员，不猜测内存偏移、不修改供应商库。原厂解析函数通过已核对的导出符号调用，以避免 SDK 老 protobuf 头文件与系统版本冲突。构建时要求上述完整库哈希一致，其他版本拒绝构建，应单独审核。现有加载器继续核对实际 SDK 库和模块文件哈希。

本次修复没有恢复已删除的归位跟踪误差保护，也没有改变目标发送、运动速度、记录按键或相机配置。
